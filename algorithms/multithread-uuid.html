多线程汇总与一个不会重复的 id

一个装 20 亿个字符串的列表，每个串是若干单词用逗号连起来的，要并行切词、统计每个单词一共出现多少次，最后交出一张汇总表，机器允许开 100 个线程。另一道题看起来毫无关系：设计一个每秒发几百万亿个 id、并且理论上绝不允许重复的系统。两道题的答案都落在一个词上：先各自记账，最后对一次总账。

零、加锁的直觉是错的

20 亿个字符串，每个最长 1000 字节，串与串之间互不相干，切词这件事天然可以拆开并行。最顺手的写法是开一堆线程，每个线程读到单词就锁住那张公共的统计表加一。

跑一遍就知道这个直觉错得有多离谱。200 万行数据（约 80MB、2000 个不同的词、1500 万个词次），本机 12 核：

线程数全局一把锁各线程局部表再合并
1434.2 ms374.4 ms
2877.0 ms198.5 ms
41245.9 ms106.2 ms
81477.1 ms72.2 ms
122056.9 ms73.6 ms

全局锁那一列，线程越多越慢：12 个线程比单线程慢 4.7 倍。线程没在干活，全在排队等锁，而且互相把对方的缓存行踢来踢去，切换开销比干活本身还大。局部表那一列是正常的：12 个线程比单线程快 5.1 倍，8 个线程时到了拐点。

这两张表的差别只有一处：锁出现在什么位置。全局锁是「每处理一个单词就锁一次」，局部表是「全程不锁，最后合并时锁一次」。

一、各写各的，最后对账

把共享的那张表拆成 T 份，线程 t 只碰自己那份。统计阶段一个锁都不用，等所有线程跑完，主线程把 T 份表合并成一份。

// 每个线程先写自己的表，最后一个人汇总：锁只在合并时出现
    vector<unordered_map<string, ll>> local(T);
    vector<thread> th;
    for (int t = 0; t < T; t++) {
        th.emplace_back([&, t] {
            for (ll i = t; i < n; i += T) {       // 步长 T 取行，负载天然均匀
                const string& s = data[i];
                for (size_t p = 0; p < s.size(); ) {
                    size_t q = s.find(',', p);
                    if (q == string::npos) q = s.size();
                    local[t][s.substr(p, q - p)]++;
                    p = q + 1;
                }
            }
        });
    }
    for (auto& x : th) x.join();
    unordered_map<string, ll> all;
    for (int t = 0; t < T; t++)
        for (auto& p : local[t]) all[p.first] += p.second;

取行的时候用步长 T 而不是把列表切成 T 段，是因为每行的长度差别很大（题目里最长 1000 字节、最短几个字节）。按段切会让某个线程抽到一堆长串，别的线程早早干完闲着；按步长取行，每个线程拿到的数据量天然均匀。这一步的成本是缓存局部性变差，实测下来还是划算的。

合并阶段是串行的，但它的工作量只跟「不同词的数量」有关，跟数据条数无关。2000 个不同的词，12 份表合并 24000 次加法，几毫秒的事。

二、局部表的内存会被放大

局部表不是白拿的。串行版本只需要一份表，并行版本要 T 份，而且因为每份都在处理不同的数据段，几乎每个词都会出现在每一份表里。

用 400 万行、100 万词的词典量一遍：

线程数 T所有局部表加起来有多少条表的内存粗估
198.2 万47 MB
4252.8 万121 MB
8314.6 万151 MB
12340.1 万163 MB

串行版本只需要 100 万条，12 个线程要 340 万条，3.4 倍。增长的幅度比 T 小（不是 12 倍），因为线程各自处理的数据段不够长，很多稀有词根本没在任何一段里出现过。但趋势是明确的：线程越多，内存越涨，涨到后来被内存卡住的概率比被 CPU 卡住还大。

这也是「100 个线程」这个数字需要打折的地方。真要开到 100 个线程，表的内存就是 100 份起步，先得确认机器扛得住。8 核机器上开 100 个线程，能同时跑的只有 8 个，剩下的在等 CPU，除了把内存翻 10 倍不会有别的效果。

三、每秒几百万亿个 id

第二道题换个方向：全球使用、每秒要发几百万亿个 id（1014 量级），要求理论上绝不允许出现重复。系统只管源源不断地发 id，不需要维护任何关系。

先算 1014 是什么概念。一天有 86400 秒，这一天就要发 8.64×1018 个 id。任何「发完查一下有没有重复」的做法都行不通，查重本身就要维护一个 8.64×1018 条记录的集合，比 id 本身还大。

也先别急着上随机数。随机 id 不重复靠的是「空间大到撞不上」，那就得算清楚多大的空间才够。m 个 id 落进 b 位的空间，至少撞一次的概率约 1 − e−m²/2^(b+1)。把 m 代成一天的量：

id 位数一天发 8.64×1018 个，撞上的概率
64 位1.000（数学上必然）
96 位1.000
122 位（UUID v4 的随机部分）0.9991
128 位0.1039
256 位0.000

结论很刺眼：题面给的并发量下，128 位的纯随机 id 一天之内有 10% 的概率撞上一次，而 UUID v4 的 122 位随机部分几乎是必然要撞。日常系统里 UUID 够用，是因为一天发的量比这少好几个数量级；把并发提到 1014，「随机够大所以不会重」这句话就不再成立了。

这套公式可以拿缩小版验证：48 位的空间里生成 1 亿个随机数，按公式应该撞 18 次，实测撞了 16 次，量级吻合。

四、用结构代替运气

真正能保证「绝不重复」的 id 不是随机出来的，是拼出来的。把 128 位分成三段：

1）高 64 位放时间戳，精度到纳秒。264 纳秒约 584 年，够用很久。

2）中间 32 位放机器号，能编 42.9 亿台机器。

3）低 32 位放这台机器在当前时刻的序号，每台机器每个纳秒内最多发 42.9 亿个。

这三段拼起来，唯一性是可以推出来的，不依赖概率：两台机器的机器号不同，id 一定不同；同一台机器在同一纳秒内，序号不同，id 也不同；同一台机器跨了纳秒，时间戳不同。想让 id 重复，就得让这三段同时相同，而这三段分别被编号、时钟和计数器管着，都撞不上。

// id = 时间戳(64 位) + 机器号(32 位) + 机器内序号(32 位)，拼成 128 位
    // 时间戳不同 → 不会重；时间戳相同而机器号不同 → 也不会重；两者都相同才轮到序号保证
    pair<ull, ull> nextId(ull machine, ull& seq) {
        ull ts = chrono::duration_cast<chrono::nanoseconds>(
                     chrono::system_clock::now().time_since_epoch()).count();
        ull hi = ts;                                            // 高 64 位放时间戳
        ull lo = ((machine & 0xffffffffULL) << 32)              // 低 32 位放机器号
               | (seq++ & 0xffffffffULL);                       // 再低 32 位放序号
        return {hi, lo};
    }

    // 号段模式：每台机器先向中心领一段 [base, base+step)，本地发完再领下一段
    ull alloc() {
        if (cur == limit) {                         // 本段发完了
            lock_guard<mutex> lk(mtx);
            base = nextBase;                        // 中心只维护一个「下一段从哪开始」
            nextBase += step;
            cur = base; limit = base + step;
        }
        return cur++;
    }

剩下的问题只有吞吐。实测单机生成 128 位 id（只写进内存，不含落盘和网络）是 2.19 亿个每秒。按这个速度，每秒 1014 个需要 46 万台机器。这个数字不算离谱，但它说明「一个不重复的 id」这件事的可行性完全建立在水平扩展上，没有哪一台机器能单独扛住。

还有一种更省的做法叫号段。每台机器不自己拼时间戳，而是先向中心申请一段连续编号 [base, base + step)，本地从这段里挨个发，发完再申请下一段。中心只维护一个「下一段从哪开始」的变量，每秒被访问的次数等于机器的数量而不是 id 的数量。号段用完了继续领，天然不会有空洞以外的重复。

并发实验台

数据是上面那张 200 万行测试的实测值。切换线程数，看两种写法的时间与加速比怎么变。

复杂度分析

做法时间空间
全局锁逐词加一O(N) 次加锁，实际被锁竞争拖慢O(不同词数)
局部表 + 合并O(N/T) 每线程 + O(T·V) 合并O(T·V)，V 是不同词数
生成一个结构化 idO(1)O(1)
号段模式发一个 idO(1) 均摊，每 step 个才访问一次中心O(1)

局部表方案的两项要一起看。并行部分按 T 分掉，是 O(N/T)；合并部分跟不同词的个数 V 有关，是 O(T·V)。V 很小（比如这里 2000 个词）时合并可以忽略；V 涨到几千万时，合并本身就是主要开销，届时要改成并行合并或者分层合并。

空间那一项 O(T·V) 是并行统计的真实成本。串行版本的 O(V) 看着更省，但它在时间上给不出任何东西。

总结

并行统计的关键不在线程模型，而在「锁放在哪」。每个词都锁一次的写法，线程越多越慢，12 个线程比单线程慢 4.7 倍；把共享表拆成 T 份、最后合并一次的写法，12 个线程拿到 5.1 倍加速，拐点在 8 线程附近。局部表的代价是内存涨到 3.4 倍左右，线程数不能凭「机器允许开 100 个」就往上堆。

id 那半页的关键不在生成速度，而在唯一性的来源。并发到每秒百万亿时，128 位纯随机 id 一天有 10% 的概率撞上，122 位的 UUID v4 几乎必然要撞，随机这条路直接出局。改用「时间戳 + 机器号 + 序号」拼出来的结构化 id，唯一性可以逐段推出来，不靠概率；单机 2.19 亿个每秒，撑起 1014 需要 46 万台机器，靠号段模式把中心点从「每个 id 一次」降到「每台机器一段一次」。

两道题共用一句话：共享的东西越少，能拆开的部分就越多。统计里共享的是那张表，id 里共享的是那个「下一个可用编号」的计数器。
