线段树：把范围操作拆到边界

要回答的东西太杂，一个懒标记装不下：一段上有几款不同的雷、每个位置各自的值。这种时候换个方向，让范围操作只落在常数个位置上，剩下的就是最普通的线段树。

零、背景

懒标记能成立，前提是「这段怎么样」能用很少几个数表示，而且两个儿子合并起来方便。区间和可以，颜色集合可以（压成掩码），但有两类东西不行。

一类是「这段上有多少种不同的东西」。甲段有 3 种、乙段有 3 种，合起来可能是 3 种也可能是 6 种，看它们撞不撞，光靠各自的种类数推不出来。

另一类是「每个位置各自是多少」。这类信息压根没有合并的说法，只有叶子才有。

但这两道题的操作都很整齐：虽然一次改的是一整段，真正「变了关系」的位置只有常数个。把线段树建在那些位置上，题目就退化成单点修改加区间求和。

一、两道题

  • 贪婪大陆（洛谷 P2184）：n 个格子，开始都没有雷。操作 1 l r 在 [l, r] 上放一款新型地雷，每一款都是全新的，不是替换掉旧雷；操作 2 l r 问 [l, r] 上共有多少款不同的雷。n、m 到 10⁵。
  • 无聊的数列（洛谷 P1438）：长度 n 的数组 arr，操作 1 l r k d 把 arr[l..r] 依次加上首项 k、公差 d 的等差数列，操作 2 p 查 arr[p] 的值。n、m 到 10⁵。

第一题的题面给了个例子：先放一款盖住 [3, 6] 的雷（叫它 A），再放一款盖住 [3, 4] 的雷（叫它 B）。这时格子 3、4 上各有 A、B 两款，格子 5、6 上只有 A。查 [4, 5] 返回 2，查 [5, 6] 返回 1。

二、贪婪大陆：一款雷只动两个位置

「在 [l, r] 上放一款雷」，如果老老实实记下来，就是往 r − l + 1 个格子上各挂一个编号。n 和 m 都是 10⁵ 时最坏要挂 10¹⁰ 条记录，折 37.3 GB，做不到。

换个角度问问题：这一款雷算不算盖在查询区间 [ql, qr] 上？雷的位置由它的左端点 a 和右端点 b 定下来，它和 [ql, qr] 有交集，当且仅当 a ≤ qr 且 b ≥ ql。位置之外的信息一概不需要。

两个条件分别数一遍：左端点不超过 qr 的雷有多少款，右端点小于 ql 的雷有多少款。后者一定是前者的子集（a ≤ b < ql ≤ qr 推出 a ≤ qr），所以相减剩下的正好是「左端点 ≤ qr 且右端点 ≥ ql」的那些，也就是盖在查询区间上的那些。

线段树上就只要两个计数器：每个位置有多少个雷的左端点、多少个雷的右端点。放一款雷是两个单点加，查询是两次区间求和。

const int MAXN = 100001;

    // starts[i]：i 号范围上有多少个雷的左端点
    // ends[i]：i 号范围上有多少个雷的右端点
    int starts[MAXN << 2];
    int ends[MAXN << 2];

    void up(int i) {
        starts[i] = starts[i << 1] + starts[i << 1 | 1];
        ends[i] = ends[i << 1] + ends[i << 1 | 1];
    }

    // jobt 等于 0 时给左端点记一次，等于 1 时给右端点记一次
    void add(int jobt, int jobi, int l, int r, int i) {
        if (l == r) {
            if (jobt == 0) {
                starts[i]++;
            } else {
                ends[i]++;
            }
        } else {
            int mid = (l + r) >> 1;
            if (jobi <= mid) {
                add(jobt, jobi, l, mid, i << 1);
            } else {
                add(jobt, jobi, mid + 1, r, i << 1 | 1);
            }
            up(i);
        }
    }

    // jobt 等于 0 时数左端点的个数，等于 1 时数右端点的个数
    int query(int jobt, int jobl, int jobr, int l, int r, int i) {
        if (jobl <= l && r <= jobr) {
            return jobt == 0 ? starts[i] : ends[i];
        }
        int mid = (l + r) >> 1;
        int ans = 0;
        if (jobl <= mid) {
            ans += query(jobt, jobl, jobr, l, mid, i << 1);
        }
        if (jobr > mid) {
            ans += query(jobt, jobl, jobr, mid + 1, r, i << 1 | 1);
        }
        return ans;
    }

题面那个例子走一遍：先放 [3, 6] 再放 [3, 4]，这时位置 3 上有 2 个左端点、位置 4 上有 1 个右端点、位置 6 上有 1 个右端点。查 [4, 5] 时左端点 ≤ 5 的有 2 个，右端点 < 4 的有 0 个，答案 2；查 [5, 6] 时左端点 ≤ 6 的有 2 个，右端点 < 5 的有 1 个，答案 1。都对上了。

// 新增一款盖住 l..r 的雷：只有两个端点会动
    void addBomb(int l, int r, int n) {
        add(0, l, 1, n, 1);
        add(1, r, 1, n, 1);
    }

    // 查询 l..r 上一共有多少款雷
    int askBomb(int l, int r, int n) {
        int s = query(0, 1, r, 1, n, 1);
        // l 等于 1 时左边没有格子，不能去查空区间 [1, 0]
        int e = l == 1 ? 0 : query(1, 1, l - 1, 1, n, 1);
        return s - e;
    }

这里有个边界要单独写。l 等于 1 的时候第二项应该查 [1, 0]，而线段树不会替你处理空区间：判断 ql <= l && r <= qr 在叶子 [1, 1] 上永远不成立（要求 r ≤ 0），于是它带着同一组参数反复调用自己。实测把 [1, 0] 直接喂进去，进程段错误退出，就是栈被递归撑爆了。查一次只有 0 个右端点，干脆特判掉。

实测：n = m = 16000、每次操作盖住大半段，逐段扫描的暴力 11.36 ms，线段树 3.40 ms。n = m = 10⁵ 时 23.22 ms。

每一根横条是一款雷，蓝框是这次查询的范围。下面两行是线段树上真正存的东西：每个位置上有几个左端点、几个右端点。答案就是把第一行「≤ r」的和减去第二行「< l」的和。

三、无聊的数列：差分上只有三个位置在动

第二题的操作读起来比第一题还麻烦：区间里每个位置加的数都不一样。但位置之间的差是固定的，第 j 个位置加的是 k + d(j − l)，相邻两项的差只多了 d。换成差分的语言，这就是一次区间加常数。

把数组换成差分数组 d[i] = a[i] − a[i−1]，整个操作拆成三句话：

  1. d[l] 加上 k。原来 a[l] 比 a[l−1] 多出来的就是 k，加完还是。
  2. d[l+1] 到 d[r] 每个加上 d。这一段内部相邻两项的差都多了 d。
  3. d[r+1] 减去末项 k + d(r − l)。r 之后的位置不该受影响，把多出来的那一截减回去。

查询 arr[p] 就是 d[1] 一直加到 d[p]：差分数组的前缀和等于原数组。于是线段树建在差分数组上，支持区间加与区间求和，查询变成一次前缀和。

const int MAXN = 100001;

    // 线段树建在差分数组上，维护一段差分值之和
    int diff[MAXN];
    long long sum[MAXN << 2];
    long long addv[MAXN << 2];

    void up(int i) {
        sum[i] = sum[i << 1] + sum[i << 1 | 1];
    }

    void lazy(int i, long long v, int n) {
        addv[i] += v;
        sum[i] += v * n;
    }

    void down(int i, int ln, int rn) {
        if (addv[i] != 0) {
            lazy(i << 1, addv[i], ln);
            lazy(i << 1 | 1, addv[i], rn);
            addv[i] = 0;
        }
    }

    void build(int l, int r, int i) {
        if (l == r) {
            sum[i] = diff[l];
        } else {
            int mid = (l + r) >> 1;
            build(l, mid, i << 1);
            build(mid + 1, r, i << 1 | 1);
            up(i);
        }
        addv[i] = 0;
    }

    void add(int jobl, int jobr, long long jobv, int l, int r, int i) {
        if (jobl <= l && r <= jobr) {
            lazy(i, jobv, r - l + 1);
        } else {
            int mid = (l + r) >> 1;
            down(i, mid - l + 1, r - mid);
            if (jobl <= mid) {
                add(jobl, jobr, jobv, l, mid, i << 1);
            }
            if (jobr > mid) {
                add(jobl, jobr, jobv, mid + 1, r, i << 1 | 1);
            }
            up(i);
        }
    }

    long long query(int jobl, int jobr, int l, int r, int i) {
        if (jobl <= l && r <= jobr) {
            return sum[i];
        }
        int mid = (l + r) >> 1;
        down(i, mid - l + 1, r - mid);
        long long ans = 0;
        if (jobl <= mid) {
            ans += query(jobl, jobr, l, mid, i << 1);
        }
        if (jobr > mid) {
            ans += query(jobl, jobr, mid + 1, r, i << 1 | 1);
        }
        return ans;
    }
// 在 l..r 上依次加上首项 k、公差 d 的等差数列
    void addArith(int l, int r, long long k, long long d, int n) {
        long long e = k + d * (r - l);
        add(l, l, k, 1, n, 1);
        if (l + 1 <= r) {
            add(l + 1, r, d, 1, n, 1);
        }
        if (r < n) {
            add(r + 1, r + 1, -e, 1, n, 1);
        }
    }

    // 单点查询：差分数组的前缀和就是原数组
    long long askValue(int p, int n) {
        return query(1, p, 1, n, 1);
    }

这里有个细节：r 等于 n 时根本就没有 r + 1 号位置，第三步要跳过；l + 1 大于 r 时第二步的区间是空的，也要跳过。这两处不判，下标直接越界。

实测：n = m = 16000、每次操作盖住大半段，逐格加等差数列的暴力 19.06 ms，线段树 5.27 ms。n = m = 10⁵ 时 37.38 ms。

和上一页那道开关一样，这里的和必须是 64 位。按题目上限构造最坏输入：n = 10⁵，10⁵ 次操作都是「整个数组加首项 1000、公差 100」，最后一个位置的真实值是 1000090000000；换成 int 累加得到 −637379968，符号都翻过来了。

第一行随 n 变大越来越难抓，从 65.12% 掉到 10.68%。两种写法只在「恰好有一款雷的右端点落在 l 这个位置上」时才有差别，n 越大这件事越不容易碰上。这类靠边界撞上的错法都有一个通病：值域一宽，抓到的概率就往下掉。

第二行反过来，88% 起步而且几乎不随 n 变。它错的是整个式子，跟边界撞不撞没关系，只要数据里有雷就露馅。

无聊的数列那三行都在 65% 以上。位置的判定多，n 越大一次操作覆盖的位置越多，少改一处立刻在后续查询里显出来。末项那条从 65.60% 涨到 77.15%，是因为 r 变大时末项更大，减错了更明显。

六、总结

两道题的共同点是「范围上的操作最后只落在常数个位置上」。贪婪大陆放一款雷动两个位置：左端点和右端点。无聊的数列加一个等差数列动三个位置：d[l]、d[l+1..r]、d[r+1]。

反过来说，这两道题要的东西本身就合并不了。贪婪大陆问的是「有几款不同的雷」，无聊的数列问的是每个位置各自的值，都不是一个「段上的量」。与其硬造一个能合并的东西，不如把操作拆开。

差分和端点计数其实是一件事的两种面貌，都在回答「这一步之后，相邻两项的关系变了多少」。下一次遇到范围操作里有「不一样的东西」，先数一数它到底动了哪几个位置。

最后

两个坑。一是贪婪大陆里 l 等于 1 时要跳过第二项查询，空区间在线段树里下不了台。二是无聊的数列里 r 等于 n 时没有 r + 1 号位置，那个单点加要跳过；同一处代码里的 l + 1 大于 r 时，那个区间加也要跳过。
