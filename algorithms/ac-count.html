AC 自动机：fail 反图汇总词频

文章走完一遍，每个位置只知道「最后落在哪个节点」。一个短目标串的出现次数并不在这个节点上，它散落在所有以它为后缀的节点里。把这笔账一次收回来，靠的是 fail 边反过来长成的那棵树。

零、题目的要求

题目给 n 个目标串和一篇大文章，要输出每个目标串在文章里各出现了几次。

麻烦的地方在于一次落点对应好几个目标串。文章里出现 "aab" 的时候，"ab" 和 "b" 也各出现了一次。AC 自动机走到 "aab" 的结尾节点，这个节点只代表 "aab" 结束了；"ab"、"b" 的次数藏在它的 fail 链上。

朴素做法顺着这个思路写：每走一个字符，落到节点 u，然后沿 fail 链一路往上，把链上每个节点的计数都加一。它是对的，代价却不固定——链有多长就要加几次。目标串长 200、文章 106 个字符时，链上每步都要退满，实测一次要 208.542 毫秒，走了 199980100 步。专门的模板题就是卡这个写法的。

一、fail 边反过来是一棵树

先看清 fail 边的形状。除根之外的每个节点恰好有一条 fail 边指向别的节点，而且 fail 目标的层数严格更小：fail 指向的是自己的一个真后缀，真后缀一定更短。层数严格递减意味着顺着 fail 边走不可能回到自己，也就没有环。

节点数是 cnt + 1，fail 边有 cnt 条，连通且无环，这就是一棵树。根的 fail 指向自己（代码里写成 0），其余边按 fail[i] → i 反过来挂，得到的是同一棵树的另一种连法。

实测那棵 152118 个节点的自动机，fail 边正好 152118 条，等于节点数减一。

二、文章只记单点词频，汇总留给树

既然一次落点的账散在 fail 链上，那么把两件事分开：

1）走文章时，只让当前落到的节点加一，得到一个单点词频。这一步和上一页的匹配循环一模一样，每个字符固定一次访问。

2）文章走完之后，沿 fail 反图做一次后序遍历，把自己的词频加上所有孩子的词频。加完之后的数字就是答案。

为什么这样对？节点 u 的 fail 后代，恰好是那些「以 u 对应串为后缀」的目标串前缀。文章里每个落到后代上的位置，都意味着 u 对应的串在那个位置出现过一次。把后代上的单点计数全加起来，正好是 u 的出现次数。

拿 {"he","she","his","hers"} 走 "ushers" 看一遍。9 个节点走完，单点词频是：根 1，s 1，sh 1，she 1，her 1，hers 1，he 与 h、hi、his 都是 0。

把 fail 边反过来挂：she 的 fail 是 he，所以 she 挂在 he 下面；hers 的 fail 是 s，所以 hers 挂在 s 下面。he 自己的单点词频是 0，它靠孩子 she 带上来的 1 得到 1；s 自己的是 1，加上 hers 带上来的 1 得到 2。根收下五个孩子，1 + 1 + 1 + 2 + 0 + 1 得到 6，正好是文章长度。

三、汇总的写法

反图用链式前向星存，先给每个节点补一条从 fail[i] 到 i 的边：

// fail 反图用链式前向星存，边一律从 fail[i] 指向 i
    void addEdge(int u, int v) {
        nxtE[++edge] = head[u];
        head[u] = edge;
        to[edge] = v;
    }

    // 走完文章之后，把每个节点的一条 fail 边加成反向边
    void buildFailTree() {
        for (int i = 1; i <= cnt; i++) {
            addEdge(fail[i], i);
        }
    }

遍历这棵树要注意递归深度。fail 树在最坏情况下是一条长为节点数的链，递归会爆栈，所以改成用显式栈模拟后序：第一次遇到节点时把它的孩子全部压栈，第二次回到这个节点时，孩子都已经处理完，把它们的词频加进来。

// 用栈模拟后序遍历 fail 反图：第一次碰到孩子，第二次回来时才把词频往上传
    void gather(int root) {
        int r = 0;
        box[r++] = root;
        while (r > 0) {
            int cur = box[r - 1];
            if (!visited[cur]) {
                visited[cur] = true;
                for (int i = head[cur]; i > 0; i = nxtE[i]) {
                    box[r++] = to[i];
                }
            } else {
                r--;
                for (int i = head[cur]; i > 0; i = nxtE[i]) {
                    hits[cur] += hits[to[i]];
                }
            }
        }
    }

把三件事串起来看耗时：那棵 152118 个节点、文章 106 字符的数据上，插入 0.891 毫秒，建 fail 9.92 毫秒，匹配 15.97 毫秒，建反图 0.397 毫秒，汇总 2.592 毫秒。

常见的错法是跳过汇总，直接输出单点词频。短的目标串当场全错：a1~a200 那组里 a1 的单点计数是 1，正确答案是 1000000。长串反而碰巧对：它后面没有更长的串可以继承，单点计数就是它的出现次数。4000 组随机数据里 53.60% 的组答案不一样，比例看着不过半，是因为随机数据里模式串之间很少有后缀关系。

沿 fail 反图逐节点回填

每点一步处理一个节点，橙色是当前节点，上行的数是单点词频、下行的数是它当前的汇总值。切到「不汇总」，看哪些串的答案还是 0。

两条路线的加法次数

文章全是一个字符，目标串是它的前缀。每点一步读一个字符，看这一步绕了几层、累计绕了多少层。

四、复杂度分析

做法关键操作时间空间
命中就沿 fail 链累加每个位置把 fail 链走一遍O(文章长度 × 最长串长)O(节点数)
只记单点词频每个字符一次计数O(文章长度)O(节点数)
fail 反图一遍树遍历每个节点进出一次，每条边看一次O(节点数)O(节点数)
合计（优化版）建机 + 匹配 + 汇总O(26 × 总字符数 + 文章长度)O(26 × 总字符数)

绕圈那一步的代价取决于数据形状：a、aa、…、a200 这种互为前缀的目标串会把链拉到 200 层，文章 106 个字符就是 2×108 次加法；随机字母的目标串链长只有几层，同一份代码看着没问题。汇总那一侧不管数据怎么长都是每个节点一次，实测 152118 个节点 2.592 毫秒，反图的三张表各占节点数级别的 int 空间。

总结

短目标串的次数被长串的路径盖住了。落点只说明「有一个目标串在这里结束」，其余那些以它为后缀的串要额外记账。

分开记：走文章只给落点加一，得出单点词频；再沿 fail 反图后序遍历一次，把孩子的计数往父亲上搬。fail 边严格往浅层指，反过来就是一棵树，节点数减一条边。

两边的复杂度都变干净了：匹配 O(文章长度)，汇总 O(节点数)，一起是 O(26 × 总字符数 + 文章长度)；绕圈的写法最坏要乘上最长串长，同一份数据 208.542 毫秒对 0.001 毫秒。

下一节换另一类需求：不是事后统计，而是走文章时随时要知道「现在有没有命中」。那时的优化点在建机阶段，把标记提前推到该负责的节点上。
