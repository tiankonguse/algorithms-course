贪心：跳步与反悔

前面的贪心都是定了就不改。这两题不一样：一个发现某条路根本不必走，整段跳过去；另一个敢于先把选择记下来，遇到更好的就把差的撤回。

零、橘子不一个个吃

厨房里有 n 个橘子，每天只能选一种吃法：吃掉 1 个；或者 n 是 2 的倍数时吃掉 n/2 个；或者 n 是 3 的倍数时吃掉 2×(n/3) 个。问吃完的最少天数。

顺着题意写转移很容易：设 f[i] 是 i 个橘子的最少天数，从 f[i-1] 继承一天，i 是 2 的倍数时再从 f[i/2] 继承一天，i 是 3 的倍数时从 f[i/3] 继承一天。这样从 0 递推到 n。

问题在 n。它的上限是 2×109，逐个推过去要填二十亿个格子。这条路走不通。

回头看第一条吃法：吃掉 1 个橘子。它是唯一一个只能减少 1 的吃法，进展最慢。既然第二、第三条吃法都是按比例减，那么花几天把橘子数调整成 2 或 3 的倍数，换来一次按比例减，一定比一直一个个吃划算。

所以每一步只有两条路可走：

1）花 n%2 天，把橘子吃成偶数，再花 1 天吃掉一半，剩下 n/2 个。这条路的代价是 n%2 + 1 + f(n/2)。

2）花 n%3 天，把橘子吃成 3 的倍数，再花 1 天吃掉三分之二，剩下 n/3 个。代价是 n%3 + 1 + f(n/3)。

「一个个吃」这条最自然的路，整段被跳过去了。它退化成了前两条路里的调整步骤。

这样算为什么快：n 每走一步至少除以 2，展开的深度只有 log n 量级；同一个 n 会被不同的路径重复问到，记忆化挡住重复计算之后，状态数只剩 O(log² n) 量级。

// n 个橘子，每天可以吃 1 个；n 是 2 的倍数时吃掉 n/2 个；
    // n 是 3 的倍数时吃掉 2*(n/3) 个。问吃完的最少天数
    unordered_map<int, int> memo;

    int minDays(int n) {
        if (n <= 1) {
            return n;
        }
        if (memo.count(n)) {
            return memo[n];
        }
        // 花 n%2 天把橘子吃成偶数，再一次干掉一半
        // 或者花 n%3 天吃成 3 的倍数，再一次干掉三分之二
        int ans = min(n % 2 + 1 + minDays(n / 2), n % 3 + 1 + minDays(n / 3));
        memo[n] = ans;
        return ans;
    }

实测 n=103 填 27 个状态，n=105 填 74 个，n=109 填 240 个，n=2×109 填 257 个，耗时 0.0087 ms。作为对照，逐个数的递推在 n=107 上就要 16.5 ms，再大十倍就慢到没法用。

两个错法：漏掉「凑倍数那几天」，直接写 1 + min(f(n/2), f(n/3))，两万组随机 n 全错，n=5 就能看出差别（正解 4，它给 3）；只走一半那条路，错 99.96%。

题面样例对得上：minDays(6) = 3、minDays(10) = 4、minDays(56) = 6、minDays(1000) = 10。答案增长得极慢，n 从 106 到 2×109 只从 20 天涨到 32 天。

一、课程表：选进来的还能退回去

第二题：n 门课，每门有上课天数和最晚完成时间，学期从第 1 天开始，不能同时上两门，问最多能上几门。

朴素做法是枚架子集再检查可行性，2n。

第一件事是定顺序：按最晚完成时间从早到晚处理。这个顺序是安全的，因为任何一套合法方案，把选中的课按最晚完成时间重排一下仍然合法，先到期的先上只会让每门课更早结束。

第二件事才是这题的关键。按顺序往下走，遇到一门塞不下的课，直觉是放弃它。可还有一条路：看看已经选中的课里，有没有哪一门比它还长。如果有，把那门踢掉、换成现在这门，门数不变，而总用时变短了。总用时变短只会让后面的课更容易塞进去，所以这个替换不会让结果变差。

容器要能随时取出「已选课里最长的那门」，用大根堆。时间不够时看一眼堆顶就够了，比它长的课也只有它一门值得考虑。

// courses[i] = {这门课要上几天, 最晚哪天完成}
    int scheduleCourse(vector<vector<int>>& courses) {
        int n = courses.size();
        sort(courses.begin(), courses.end(), [](const vector<int>& a, const vector<int>& b) {
            return a[1] < b[1];
        });
        // 已经选中的课，按时长放，最长的那门在堆顶
        priority_queue<int> heap;
        int time = 0;
        for (int i = 0; i < n; i++) {
            int d = courses[i][0], last = courses[i][1];
            if (time + d <= last) {
                heap.push(d);
                time += d;
            } else if (!heap.empty() && heap.top() > d) {
                // 已选里最长的比现在这门还长，把它换掉：门数不变，总时长变短
                time += d - heap.top();
                heap.pop();
                heap.push(d);
            }
        }
        return heap.size();
    }

这里有个细节：heap.top() > d 写成 >= 完全等价。相等时 time 加上 0，弹出和压入的是同一个值，堆的内容和总用时都不变。实测两万组随机数据 0.00% 差异。这种地方不用改，但知道它为什么一样，比记住「要写大于」踏实。

两个错法：不反悔，塞不下就跳过，值域 1 到 8 时错 11.15%，值域放大到 500 时错 9.57%；按上课天数升序排，错 38.55% 到 43.58%。后一个错法错得更多，因为短课虽然好塞，但截止时间近的课会白白错过。

样例核对：[[100,200],[200,1300],[1000,1250],[2000,3200]] 答案是 3；[[3,2],[4,3]] 是 0，两门课都来不及；[[5,5],[4,6],[2,6]] 是 2，靠的就是那一次反悔。

实测 n=1000 耗时 0.10 ms，n=10000 是 1.16 ms，n=100000 是 10.25 ms。堆里最多留 n 门课，每门进出各一次。

二、两个演示

演示 A　吃橘子：每一步只留两条分支

每一帧比较两条分支的代价，橙色框是这条路选中的那条。左边那串是已经走过的橘子数。

演示 B　课程表：塞不下的时候回头看一眼

课程按最晚完成时间排好序逐门处理。蓝色是当前已选课程的时长，橙色是刚处理完那门的时长，绿色是替换进来的新课。

三、复杂度分析

题目关键操作时间空间
吃掉 N 个橘子两条分支的记忆化递归O(log² n)，每个状态两次转移O(log² n)，记忆化的格子数
吃掉 N 个橘子（逐个数递推）从 0 推到 nO(n)O(n)
课程表 III按最晚时间排序 + 每门课的堆操作O(n log n)，每门课最多一次进堆一次出堆O(n)，堆最多装下所有课

橘子那题的复杂度看着奇怪，实际状态数实测只有几十到两百多个：每一步把 n 除以 2 或除以 3，能走到的 n 是有限个。课程表那题把两条分支合起来看，就是一次排序加 O(n) 次堆操作。

四、总结

1）橘子那题的关键是认出「一个个吃」不配当主干。它只在把橘子数调成 2 或 3 的倍数时有价值，于是每一步只剩两条分支，深度降到 log n，再配上记忆化就能吃下 2×109。

2）课程表那题的关键是允许撤回：塞不下时，先看已选里最长的那门是不是比现在这门还长，是就换掉。门数不变、总用时变短，后面只会更宽松。

3）反悔能不能成立，取决于「已选集合」这个状态够不够描述过去。课程表里后面只关心「到现在用了多少天」，所以踢掉哪一门不影响别的东西。换成别的题未必成立，得逐题看。

4）两题各有一个不显眼的坑：橘子那题漏掉凑倍数的那几天会全错；课程表的反悔条件是严格大于还是大于等于，其实一样，别在这上面浪费时间去调。
