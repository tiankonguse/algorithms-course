合并两个有序链表

上一讲反转一条链，动的是同一条链内部的指针。这一讲把两条链并成一条，动的是链与链之间的连接。两步操作都很短，但把「变量里装的是地址」这件事又往前推了一层：合并的时候，改一个 next 就等于把一整段链从一条搬到另一条上。

零、背景

链表题在笔试面试里出现得比它应有的难度更频繁。原因还是那句：写对需要真的理解内存，写错又非常容易。

合并这条题多了一个隐含要求，题目原话是「新链表是通过拼接给定的两个链表的所有节点组成的」。它说的是复用，不是抄值。这个要求不会单独标红，但按抄值写就丢掉了整道题的考点。

这一讲顺着走四步：先摆两种绕路的写法并量一下代价，再讲双指针原地拼接，然后是用虚拟头结点和递归写的两个版本，最后把「两条」换成「多条」。

一、问题

给两个升序链表的头节点 head1、head2，把它们并成一个升序链表并返回新头。新链表由原来的节点拼接而成，不许新开节点。合并两个有序链表是它的模版题。

下图是一个具体的例子。两条链各自升序，各自内部不需要动，要动的是它们之间的连接。

目标是 O(n + m) 时间、O(1) 额外空间。n 和 m 是两条链的长度。

二、两种绕路的写法

第一种是把它当成数组题：把两个链表的值全倒进一个数组，sort 一遍，再穿成新链。这样写能过，代价是没用到「两条链本身已经有序」这件事。

第二种用到了有序，两个指针比大小取小的那个，但每取一个就 new 一个新节点。这版的问题是把能复用的节点全扔了。

同一份数据（n = m = 200000）实测：原地复用 1.95 ms，新建节点 13.46 ms（慢 6.9 倍，多占 6.1 MB），数组加排序 12.66 ms（慢 6.5 倍）。

两个慢版本慢在不同的地方。排序那版是复杂度输了，O((n+m) log(n+m)) 对 O(n+m)；新建节点那版复杂度没输，输在四十万次 new 和随之而来的缓存不命中。

顺带记一个数：一个 new 出来的节点是 16 字节，是 int 的四倍，因为多了一根指针。

三、双指针原地拼接

关键的一句话很短：两条链各自升序，所以全局最小的那个只可能是两个头里较小的那个。

取走它之后，剩下的局面和原来一模一样，还是两条升序链，加上一个已经排好的尾巴。于是同一句话可以再说一遍，直到某条链空掉。

三个指针就够：pre 指向已合并部分的最后一个节点，cur1、cur2 分别指向两条链当前的头。

struct ListNode {
        int val;
        ListNode* next;
        ListNode(int v) : val(v), next(nullptr) {}
    };

    ListNode* mergeTwoLists(ListNode* head1, ListNode* head2) {
        if (head1 == nullptr || head2 == nullptr) {
            return head1 == nullptr ? head2 : head1;
        }
        ListNode* head = head1->val <= head2->val ? head1 : head2;
        ListNode* cur1 = head->next;
        ListNode* cur2 = head == head1 ? head2 : head1;
        ListNode* pre = head;
        while (cur1 != nullptr && cur2 != nullptr) {
            if (cur1->val <= cur2->val) {
                pre->next = cur1;
                cur1 = cur1->next;
            } else {
                pre->next = cur2;
                cur2 = cur2->next;
            }
            pre = pre->next;
        }
        pre->next = cur1 != nullptr ? cur1 : cur2;
        return head;
    }

这里有个细节值得停一下。head 选完之后，代码并没有把两条链「归位」：cur1 顺着 head 所在那条链往下走，cur2 指向另一条。所以 cur1 不一定是第一参数那条链，head == head1 那个三元表达式就是在处理这件事。

三处最容易写错的地方：

一是 cur1 = head->next 不能写成 head1->next。当 head 来自第二条链时，后者会让 cur1 从第一条链的头开始，而第一条链的头已经被当成了 cur2，两条链会自己接成环。

二是 pre = pre->next 不能忘。忘了 pre 就一直停在 head 上，后面的每次 pre->next = ... 都在覆盖同一个位置，最后只有两个节点挂在结果上。

三是循环结束后的那一句。两条链里只要还有一条没走完，剩下的整段可以直接挂上去，不用再比，它们本来就比已合并部分的所有元素都大。

比较次数也可以算清楚。每轮取走一个节点，取到某条链空为止，所以上界是 n + m − 1，下界是 min(n, m)。实测 n = m = 1000：值域 10⁶ 的随机数据平均 1998.0 次，几乎打满上界；两条链严格交替时正好 1999 次；一条链整体小于另一条时 1000 次。

随机数据为什么也几乎打满：两条随机升序链在值域很大时，绝大多数位置都是交错的，要走到很靠后的地方才会出现「一条先耗尽」。n = 1000、m = 100 时平均降到 1090.8 次，因为短的那条很快就耗尽了。

四、虚拟头结点

上面那段代码有个别扭的地方：第一个节点要单独挑出来，之后才能进循环。垫一个不存值的哨兵节点在前面，第一个节点就和后面的节点一样处理了。

ListNode* mergeTwoLists(ListNode* h1, ListNode* h2) {
        ListNode dummy(0);
        ListNode* pre = &dummy;
        while (h1 != nullptr && h2 != nullptr) {
            if (h1->val <= h2->val) {
                pre->next = h1;
                h1 = h1->next;
            } else {
                pre->next = h2;
                h2 = h2->next;
            }
            pre = pre->next;
        }
        pre->next = h1 != nullptr ? h1 : h2;
        return dummy.next;
    }

省掉的是一次分支判断和三个变量的初始化，代码短不了几行，但少了一个「只有第一次不一样」的特例，写错的机会也少一个。

这个版本还顺带修掉了一个不太显眼的问题：它是真的稳定的。课程里那个版本虽然也写了 <=，但因为 head 选定之后 cur1 的身份换到了另一条链上，遇到相等元素时优先取的是「被换到 cur1 位置的那条」，而不是第一条链。

实测：n = m = 8、值域 5、2000 组随机数据，看同值元素是否保持「来自第一条链的排在前面」。课程写法有 275 组反了，写成 < 更差，1725 组反了，哨兵版 0 组。

什么时候在乎这个？合并之后的链还要拿去做按值分桶、按原序输出之类的事情时就在乎。题面没要求的时候两种写法都对，LeetCode 那道题不检查。

五、递归写法

换个说法描述同一件事：合并两条链，等于取较小的那个头，再合并「它的剩余部分」和「另一条链」。这句话本身就是递归定义，照着写就行。

ListNode* mergeTwoLists(ListNode* h1, ListNode* h2) {
        if (h1 == nullptr) return h2;
        if (h2 == nullptr) return h1;
        if (h1->val <= h2->val) {
            h1->next = mergeTwoLists(h1->next, h2);
            return h1;
        }
        h2->next = mergeTwoLists(h1, h2->next);
        return h2;
    }

干净是真干净，一个判断加两行赋值。代价在栈上：递归深度等于 n + m，因为每取走一个节点才往下走一层。实测 n + m = 250000 能过，280000 段错误（默认栈 8 MB，算下来每帧约 30 字节）。

链长由输入决定、自己控制不了的场景，还是用迭代版。

六、比赛里的数组版

new 出来的节点散在堆上，访问慢，也不好预估内存。比赛里常见的是拿数组拼出链表：val[] 存值，nxt[] 存下一个的下标，0 表示空。

const int MAXN = 200005;
    int val[MAXN], nxt[MAXN], tot;

    // 返回合并后的头节点下标，0 表示空
    int mergeTwoLists(int h1, int h2) {
        if (h1 == 0) return h2;
        if (h2 == 0) return h1;
        int head, pre;
        if (val[h1] <= val[h2]) {
            head = pre = h1;
            h1 = nxt[h1];
        } else {
            head = pre = h2;
            h2 = nxt[h2];
        }
        while (h1 != 0 && h2 != 0) {
            if (val[h1] <= val[h2]) {
                nxt[pre] = h1;
                pre = h1;
                h1 = nxt[h1];
            } else {
                nxt[pre] = h2;
                pre = h2;
                h2 = nxt[h2];
            }
        }
        nxt[pre] = h1 != 0 ? h1 : h2;
        return head;
    }

逻辑和指针版一字不差，只是 ->next 换成 nxt[]、nullptr 换成 0。上一讲那些「数组版链表」的代码，都可以直接配上这个函数用。

七、两条变多条

把 K 条升序链表并成一条，最直接的写法是拿一条答案链，依次和每条合并。问题在于第一条链会被反复扫：第 i 轮它已经攒了 (i − 1)·L 个节点，还要再和一条长为 L 的比一次。

实测 K = 1000、每条 1000 个节点（共 10⁶ 个）：依次合并 2387.9 ms、比较 500001793 次；分治 35.6 ms、比较 9974015 次；优先队列 26.6 ms。最快的和最快的差了将近七十倍。

分治做的就是把「依次」换成「两两配对，逐层往上」。每条链在每一层只出现一次，一共 ⌈log₂K⌉ 层，所以每条链只被扫 ⌈log₂K⌉ 次。

// 自底向上：每轮把相邻的两条并成一条，log K 轮之后 lists[0] 就是答案
    ListNode* mergeKLists(vector<ListNode*>& lists) {
        if (lists.empty()) return nullptr;
        int n = (int)lists.size();
        for (int step = 1; step < n; step <<= 1) {
            for (int i = 0; i + step < n; i += step << 1) {
                lists[i] = mergeTwoLists(lists[i], lists[i + step]);
            }
        }
        return lists[0];
    }

step 每轮翻倍，i 每次跳两个 step，这样一轮里相邻的两条各自合并，结果留在下标小的那个位置上。K 不是 2 的幂也没关系，落单的那条会自己留到下一层。

优先队列是另一个方向：堆里始终装着 K 条链当前的头，每次取最小的那个出来，把它所在链的下一个补进去。比较次数也是 O(N log K)，实测比分治还快一点，代价是多 O(K) 的空间。

八、最后

把这道题单独看，十几行就写完了。真正要留下的是那个判断，「最小的只可能在两个头里」，它来自「两条链各自有序」这个前提。前提一变，比如两条链无序，这句话立刻不成立，题目也就变成了另一道题。

归并排序把数组切成两半、排好、再并起来，并的那一步用的就是这里同一个「比较两头取小」的动作。后面讲排序时会再碰见它。

《完》
