状压 dp：用一个整数装下集合

动态规划的可变参数通常是一个数、两个下标、一个区间。可有一类题要问「这一堆东西里，哪些还没用过」。这个参数没法直接当数值，却可以塞进一个整数的二进制位里。塞进去之后表就建得起来了，代价是表的长度是 2 的样本数次方。

零、样本的「还能不能用」压成一位

设一个整型可变参数 status，用它的第 i 位表示第 i 个样本的状态。位是 1 还是 0，看这道题想要哪种语义：可以表示「还能用」，也可以表示「已经用过」。选哪一种都行，全篇统一就好。

k 个样本，就有 2k 种 status，取值范围 0 到 2k − 1。样本每多一个，状态数翻一倍。这就是状压 dp 的题样本量都很小的原因：一般不超过 20 个，220 约等于 106。再往上，光是把这些状态走一遍，指令条数就奔着 107 到 108 去了。

如果样本多到状压也放不下，那说明这题不该用动态规划，这时候双向广搜是个备选。

代码的推进顺序和别的 dp 没有区别：写出尝试的递归函数，加记忆化，改成严格位置依赖的表，最后看能不能做空间压缩。变的只是「状态」这个概念的形状：从一个数变成了一串二进制位。

一、两个可变参数，只缓存一个

先看题。给两个整数 n 和 m，两个玩家轮流从 1 到 n 里挑一个还没被挑走的整数，把挑走的数加到公共累加和里（两边都算）。谁在自己的回合把累加和推到不小于 m，谁赢。两个人都绝顶聪明，问先手能不能稳赢。

递归函数长这样：f(status, rest)。status 表示 1 到 n 里还剩哪些数能挑，rest 表示距离 m 还差多少。答案就是 f(全 1 的 status, m)。

这里有个可以直接省掉一维的地方。rest 不用当可变参数。已经挑走的数之和就是 1 到 n 的总和减去 status 里剩下的数之和，status 一确定，rest 就定了。既然它被 status 唯一决定，就只对 status 建表。

这条不限于这道题，所有动态规划都这么看：抓住唯一的关键可变参数，被它决定的那几个不用管。

第二句提前返回看着像个纯粹的剪枝，其实它修的是一处正确性。递归的写法是「只要存在一步走法，让对手的 f 返回 false，我就赢」。而 f 返回 false 有两种完全不同的原因：对手真的必败，和对手根本没得走。池子被掏空、却谁都没到 m，那是平局，先手不算赢。1 到 n 全加起来都到不了 m 时，局面必然是这样，所以必须先挡掉。

随手写个对拍用的暴力，很容易把「没得走」直接当成「对手输了」，结果在 20000 组随机 (n, m) 上跟正解差出 2305 组。把暴力改成「赢 / 平 / 输」三值之后归零。

代码里还有一处容易写错的地方：取走数字 i 的时候，要同时把 status 的第 i 位清掉，并把 rest 减 i。只减 rest 不清位，等于允许同一个人把同一个数挑两遍；只清位不减 rest，等于那一步白拿。

bool canIWin(int n, int m) {
        if (m == 0) return true;
        // 1~n 全加起来都到不了 m，谁也没法赢，先手当然不算赢
        if ((long long)n * (n + 1) / 2 < m) return false;
        dp.assign(1 << (n + 1), 0);
        return f(n, (1 << (n + 1)) - 1, m);
    }
// status 的第 i 位是 1，表示数字 i 还能选；第 0 位弃而不用
    // rest 是双方累加和还差多少到 m，它由 status 唯一决定，所以只缓存 status
    bool f(int n, int status, int rest) {
        if (rest <= 0) return false;
        if (dp[status] != 0) return dp[status] == 1;
        bool ans = false;
        for (int i = 1; i <= n; i++) {
            if ((status & (1 << i)) != 0 && !f(n, status ^ (1 << i), rest - i)) {
                ans = true;
                break;
            }
        }
        dp[status] = ans ? 1 : -1;
        return ans;
    }

状态数是 2n+1，多出来的那一位是第 0 位，从头到尾弃而不用。n = 20 时表长 221 个状态，每个状态一个字节，2 MB。0 表示没算过，1 和 -1 分别表示 true 和 false。用 signed char 存就够了，用 int 也行，就是浪费三倍内存。

记忆化能省多少，取决于 m 落在哪。把 n 固定成 20，让 m 从总和的 20% 走到 100%，实测访问过的状态数是这样的：

中间那段最费。m 取到总和的七成左右时访问了 704658 个状态，22.8 ms；贴着总和（m = 210）只要 28655 个状态、0.64 ms，因为先手随便挑一个，剩下的路很快就被对手封死了。顺带说一句，n = 20 时这些 m 全部是先手必败，答案都是 false。

把 n 从 1 到 14、m 从 0 扫到「总和 + 2」全部跑一遍，共 602 组，先手能赢的占 73.92%。

复杂度分析

题目时间空间
我能赢吗O(2n+1 · n)O(2n+1)

status 有 2n+1 种，每个状态枚举 n 个数，所以时间是它们的乘积。记忆化保证每个 status 只展开一次。空间就是这张表，用 signed char 存是 2n+1 字节，n = 20 时 2 MB；递归栈的深度不超过 n，因为每往下一层至少取走一个数。

这个复杂度只是个上界，实测远用不满。上面那张图里，n = 20 的九组数据最多访问 704658 个状态，只有上界 2097152 的三分之一，剩下的是被「找到一条必胜走法就 break」提前砍掉的。

总结

用整数的二进制位表示「哪些样本还能用」，可变参数就从一个集合变成了一个整数，表也就建得起来。k 个样本对应 2k 个状态，所以这类题的样本量一般在 20 以内。

建表之前先数可变参数。这道题有 status 和 rest 两个，但 rest 完全由 status 决定，表只用管 status。判断的标准是「它能不能由别的参数推出来」，能推出来的就不进状态。

递归里「对手的答案取反」要写对。取反只表示「对手不能赢」，而对手不能赢和对手必输并不等同：池子空了是平局。这道题靠一句「总和到不了 m 就直接返回 false」把这个口子堵上，拿掉它就会在总分不够的样本上答错。

加记忆化之前先想清楚：不同的递归路径会不会走到同一个 status，却带着不同的 rest。这道题不会，因为 rest 是 status 的函数；换成别的题就要小心，那样缓存单靠 status 就不够了。

下一类题的 status 换了语义，记录的是「还剩多少活没干完」。
