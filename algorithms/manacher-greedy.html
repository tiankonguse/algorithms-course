Manacher：不重叠回文子串的最多数目

把串切成若干段，每段都得是长度不小于 k 的回文，问最多能切几段。看到「最多几段」会先想到 DP，但这里每一段只要长度够就能拿，早切一段给后面留的空间更大，贪心就够了。真正要解决的是另一件事：怎么在线性时间里找到离当前位置最近的、长度够 k 的那个回文。

零、题目

给定字符串 s 和正数 k，可以随意把 s 切成多个子串，要求切出来的每个子串都是长度不小于 k 的回文，且彼此没有重合，返回最多能切出几段。

数据范围是 |s| ≤ 2000、k ≤ 2000，平方做法能过。暴力先预处理任意区间是不是回文（O(m2) 的空间），再跑一遍 DP：f[i] 表示前 i 个字符最多切几段，转移是 f[i] = max(f[i − 1], max{ f[j] + 1 | j ≤ i − k 且 s[j, i) 是回文 })。

实测这份 DP 在 m = 1000 时 0.31 毫秒，2000 时 1.70 毫秒，4000 时 17.19 毫秒，翻倍就涨到四倍。线性做法在 n = 106 上只要 6.17 毫秒。

一、贪心怎么切

维护一个位置 l，表示「已经被切掉的部分的右边界」。从 l 出发往右找离 l 最近的、长度不小于 k 的回文，把它切下来，段数加一，l 挪到这个回文右边那一格，重复到找不到为止。

为什么挑最早结束的那个？假设某个最优方案里，第一段结束得比贪心选的那段晚，那就把它换成贪心选的这段。新段的右边界只会更靠左，剩下的可切范围是原来那段的超集，后面所有段照搬过来仍然合法，段数不变。所以贪心选的第一段不亏，而它结束得最早，归纳下去每一段都不亏。

这里的 l 落在扩展串的偶数下标上，也就是某个 '#' 的位置。真实串的每个字符落在奇数下标上，所以「l 落在 '#' 上」等于说 l 就是「第 l / 2 个字符之前」这个分界点。

二、左边界为什么要跟着 l 走

找回文这件事，扩展串和 p 数组现成就有，但直接照搬会出问题：切过的部分不能再被用到。如果一个回文从 l 左边伸过来盖住了 l，它就和已经切掉的那段重合了，不合法。

所以往外扩的时候，左边界不是 0 而是 l：

while (i + len < n && i − len >= l && ss[i + len] == ss[i − len])

只有 i − len >= l 这一处和标准的 Manacher 不同。它把「回文不能越过 l」这句话直接写进了扩展条件里，比事后检查省事。

三、半径和长度差 1

len 是扩展串上的半径，真实回文长度是 len − 1，所以「长度不小于 k」写成半径就是「半径大于 k」，也就是 len >= k + 1。

半径一旦超过 k，就说明以这个 i 为中心存在一个长度不小于 k 的回文。不需要找到最长的那个，取长度刚好 k 的那个反而更有用：以 i 为中心、半径 k + 1 的回文在扩展串里盖住 [i − k, i + k]，右端点是 i + k，把切点放在这里，剩下的范围最大。

i + k 的奇偶性不好说，而 l 必须落在 '#' 上，所以返回前还差一步修正：ss[i + k] 不是 '#' 就再加 1。

把这个修正去掉，20000 组随机串里有 6.46% 会算错（字符表取 2、串长 30），把字符表放大到 26、串长 200 只剩 1.67%。

四、代码

主体就是一个 while，每次问一次「下一个回文在哪」。

// 从下标 0 开始，每次切掉一个长度 >= k 的回文，能切几个切几个
    int maxPalindromes(const string &str, int k) {
        manacherss(str);
        int ans = 0, next = 0;
        while ((next = findNext(next, k)) != -1) {
            ans++;
        }
        return ans;
    }

find 是改过左边界的 Manacher。它从 l 出发，一旦某个中心的半径超过 k 就立刻返回，不把 p 数组填完。

// 在扩展串上从 l 出发往右找，一旦有中心的半径 > k 就收工
    // 返回长度 k 的那个回文的最右下标，一定让它落在 '#' 上
    int findNext(int l, int k) {
        for (int i = l, c = l, r = l, len; i < n; i++) {
            len = r > i ? min(p[2 * c - i], r - i) : 1;
            while (i + len < n && i - len >= l && ss[i + len] == ss[i - len]) {
                if (++len > k) {
                    return i + k + (ss[i + k] != '#' ? 1 : 0);
                }
            }
            if (i + len > r) {
                r = i + len;
                c = i;
            }
            p[i] = len;
        }
        return -1;
    }

五、为什么这样是 O(n)

find 返回的位置是 i + k 或 i + k + 1，其中 i ≥ l、k ≥ 1，所以它严格大于 l。下一轮从这个更大的下标开始扫，各轮扫过的中心区间互不重叠，合起来不超过 n 个中心。

while 里真正往外扩的步数也有账可算：右边被 n 挡着，左边被 l 挡着，l 只增不减；白拿的 p[2c − i] 那部分是一步到位，不花时间。所以整趟的扩展次数是线性的。

返回 −1 的那一次会把 i 从 l 扫到 n，看着像一次平方，但它只可能出现一次，而且那一段下标后面不会再被扫第二遍。

六、三个错法

1）左边界只挡 0。切过的部分又被算进来，答案偏大。字符表 2、串长 30 时 54.77% 出错，字符表 4、串长 80 降到 29.02%，字符表 26、串长 200 只剩 7.62%。

2）阈值写成 len >= k。这样是要求真实长度不小于 k − 1，切出来的段会比正解多。三档分别是 57.23%、53.42%、28.82%，是三个错法里最容易被抓到的。

3）返回时不做奇偶修正。切点落在字母上下一次扩展就会多算或漏算一格，抓取率 6.46%、7.33%、1.67%，字母表一变大就很难抓到。

这一题的抓取率随字母表变大而下降，和随机串里能凑出多少回文直接相关：字符表越小，随机串里的回文越多，切点位置一变就容易撞出不同的答案。

逐步切分

每点一步找出一段长度不小于 k 的回文并切掉。灰底是已经切走的部分，橙框是这一步切下来的段。切到错误版本，看段数从哪一步开始和正解不一样。

七、复杂度分析

做法关键操作时间空间
区间回文表 + DP枚举每个区间的回文性，再枚举转移O(m2)O(m2)
Manacher 上贪心每轮从 l 出发扫到第一个够长的回文O(m)O(m)

贪心的每一轮把 l 往右推，各轮扫过的中心不重叠，加上扩展次数被 l 和 n 两头夹住，总共 O(m)。空间按 |s| ≤ 2000 的开法，ss 与 p 各 4003 格；把上限放到 106 也只有 2 MB 字符加 8 MB int。n = 106、k = 3 实测 6.17 毫秒，DP 那一档在 m = 4000 就到 17.19 毫秒了。

总结

贪心的依据是「早结束的段不亏」：最早结束的那段换上去，右边可用的范围只会更大。

实现上只需要在 Manacher 的扩展条件里把左边界从 0 改成 l，再把「长度不小于 k」翻译成「半径大于 k」。返回的切点要做一次奇偶修正，好让下一个 l 落在 '#' 上。

时间和空间都是 O(m)。这套「在 Manacher 上跳着找」的写法，同一趟扫描里既填 p 又直接产出切点，比先算完 p 再回头找要少一趟。
