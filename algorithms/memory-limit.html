内存限制：40 亿个数怎么数

32 位无符号整数的范围是 0 到 4294967295，一共 42.9 亿个格子。文件里正好装着 40 亿个这样的数，内存只有 1GB，甚至只给 3KB。要回答的问题有三种：哪些数没出现过、哪些数恰好出现了两次、第 20 亿小的数是几。答案全都建立在同一件事上：数一数落在某一段里的数有多少个，和这一段的格子数比一比。

零、先把账算出来

40 亿个数，每个 4 字节，文件就是 16GB。无论问什么，都必须一遍遍地扫这个文件，因为谁也装不下它。

能利用的只有值域和个数之间的差距。值域 232 有 4294967296 个格子，文件里只有 4000000000 个数，中间差着 2.9 亿。就算这 40 亿个数互不相同，也一定至少有 2.9 亿个格子空着。这条鸽巢原理是整个问题的地基。

三种问法对应三种预算：

1）谁没出现过：每个数只需要回答「出现过没有」，一个二进制位够。

2）谁恰好出现两次：每个数要区分「没出现 / 一次 / 两次 / 更多」，两个二进制位够。

3）找一个没出现过的数、或者求上中位数，内存小到只有 3KB 甚至几个变量。

一、1GB 内存，谁没出现过

开一个 232 位的位图，即 512MB。扫文件，每读到一个数就把对应位置 1。扫完之后再扫一遍位图，位为 0 的位置就是没出现过的数。

// 40 亿个 32 位整数，1 bit 一个格子就能记下谁出现过
    // 值域 2^32 → 位图 2^32 bit = 512 MB
    vector<ull> bit(1ULL << 26, 0);          // 2^32 / 64 个字
    for (ll i = 0; i < n; i++) {             // 一遍扫完文件
        u32 x = readNext();
        bit[x >> 6] |= 1ULL << (x & 63);     // 第 x 号格子置 1
    }
    for (ll w = 0; w < (1LL << 26); w++) {   // 扫位图，0 就是没出现过的数
        ull miss = ~bit[w];
        while (miss) {
            int b = __builtin_ctzll(miss);
            printf("%llu\n", (w << 6) + b);
            miss &= miss - 1;
        }
    }

内存占用正好是 232 / 8 = 536870912 字节 = 512MB，1GB 的预算用掉一半，剩下一半留给读入缓冲和程序本身，很宽裕。实测在 228 的值域上跑一遍，32MB 的位图、2.68 亿个互不相同的数、只缺 1000 个，1.04 秒扫完，缺失数一个不多一个不少。

这道题问的是「所有」没出现过的数，所以位图必须开满。如果只问「一个」，第三节的办法能把这个 512MB 砍到几 KB。

二、谁恰好出现两次：2 bit 装不下

把位图升级成 2 bit，一个数占两个二进制位：00 没出现，01 出现一次，10 出现两次，11 出现三次及以上（到 11 就不再往上加了）。

算一遍内存：232 × 2 bit = 233 bit = 1073741824 字节 = 1024MB。题目给的 1GB 是 1000MB，1024 比 1000 多出 24MB。就多这么一点，方案就得改。

出路是把值域劈成两半。第一趟只看 0 到 231−1 这一段，用一张 512MB 的 2 bit 表；第二趟只看 231 到 232−1 这一段，复用同一张表。代价是文件要读两遍，换来的是内存稳稳落在 512MB。

这种「差一点就装下」的局面在大数题里很常见。面试里把这句话说出来，等于把「我知道 1GB 到底是多少字节、也知道这张表到底多大」摆在了桌面上，比一句「用 2 个 bit 就行」结实得多。

2 bit 计数的正确性可以用一份缩小版数据验证：值域 228 上让每个数随机出现 0 到 3 次，总共 4.03 亿个数，扫出来的「恰好两次」有 67109606 个，理论值 V/4 = 67108864 个，差 742 个，相对误差 0.001%。

三、只有 3KB：分桶再二分

内存压到 3KB，位图彻底没了。这时候换个问法：不问「哪个数没出现」，只问「找一个没出现过的数」。

路子还是鸽巢原理，只是把「格子」的粒度放大。3KB = 3072 字节 = 768 个 32 位整数，正好当 768 个计数器用。把 232 的值域切成 768 段，每段 5592406 个可能的数。扫一遍文件，只统计每一段里落了多少个数。

扫完之后检查这 768 个计数器：某一段里的实际个数如果小于 5592406，这一段里必然有空洞。挑出第一段满足条件的位置，答案就落在这一段内部。

接下来在段内二分。段的长度是 5592406，log2 约 22.4，向上取整 23 轮二分就能把区间压到 1 个数。加上定位那 1 遍，总共扫 24 遍文件。

// 内存只有几个变量：二分值域，每轮重新扫一遍文件，只带一个计数器
    // 区间 [lo, hi] 里若有 cnt 个数，而这段值域有 room 个数，cnt < room 就说明这段必有空位
    ull lo = 0, hi = (1ULL << 32) - 1;
    while (lo < hi) {
        ull mid = (lo + hi) >> 1;
        ll cnt = 0;
        rewindFile();                        // 文件重新从头读
        for (ll i = 0; i < n; i++) {
            u32 x = readNext();
            if (x >= lo && x <= mid) cnt++;
        }
        if ((ull)cnt < mid - lo + 1) hi = mid;   // 左半段有空洞
        else lo = mid + 1;                       // 左半段是满的，空洞在右边
    }
    printf("%llu 没有出现过\n", lo);

二分那一步的判据只有一行：区间 [lo, mid] 里有 cnt 个数，这段值域有 (mid − lo + 1) 个格子，cnt 小于格子数就说明左半边有空洞，往左收缩；否则左半边是满的，空洞在右边。

实测（值域 228、268434456 个数、只缺 1000 个）：768 个桶每桶覆盖 349526 个值，第一遍定位到第 0 桶，桶内二分 18 轮，一共 20 遍扫完，找到 95661，验证下来这个数确实没出现过。

对照一下不分桶的裸二分：同样这份数据要扫 28 遍。多出来的 8 遍相当于 8 倍的数据读取量。值域换成真实的 232 时，3KB 版本是 1 + 23 = 24 遍，裸二分是 32 遍，差额还是 8 遍，按 16GB 的文件算就是 128GB 的读盘量。

四、只有几个变量：二分到底

连 3KB 都不给，只留几个变量，那就把第二节那 768 个计数器也省掉，一遍一遍地二分整个值域。

每一轮只用一个计数器：统计有多少个数落在 [lo, mid]。计数完立刻判断，扔掉计数，进入下一轮。32 轮之后区间长度变成 1，剩下的那个数就是答案。

这一版的空间是真正的 O(1)，代价是扫 32 遍文件。实测在 228 值域上跑 28 轮，一共 75 亿次比较，1.85 秒；换算到真实的 40 亿个数，是 32 × 40 亿 = 1370 亿次比较。

时间和内存在这里是一根滑杆两端：3KB 的桶把 32 遍压到 24 遍，几个变量则一遍都省不了。选哪一端取决于你更缺什么。

顺带把这个骨架挪去解另一个问题。上中位数是第 20 亿小的数（40 亿个数，取 rank = 231）：每轮数一数不大于 mid 的数有多少个，个数够 rank 就往左收缩，不够就往右。同一套循环、同一个计数器，改一行判断条件而已。缩小版实测：2.68 亿个数里第 134217228 小的数是 134217732，复核下来小于它的有 134217227 个、不大于它的有 134217228 个，对得上。

找缺失数实验台

值域缩到 0 到 63 便于观察，里面有 58 个数，缺 6 个。点「下一轮」看二分怎么把区间折半，每一轮都只用一个计数器。

复杂度分析

做法时间空间
位图找所有缺失O(N) 扫描 + O(2b/64) 扫位图2b bit，b = 32 时 512MB
2 bit 计数找出现两次O(N)，分两趟则 2·O(N)2·2b bit，b = 32 时 1024MB
3KB 分桶 + 桶内二分O(N·(1 + log(2b/B)))，B 是桶数O(B)，B = 768 时 3KB
几个变量 + 值域二分O(N·b)，b = 32 时 32 遍扫描O(1)

这里的 N 是文件里的数的个数，b 是值域的位数。两个数字都很关键：N 决定一遍扫描要读多少数据，b 决定要扫多少遍。值域是 32 位这件事本身就是优势，如果题面给的是 64 位整数，二分那套要扫 64 遍，位图那套的直接变成 264 个格子，两个方案同时失效。

还有一层不写在复杂度里但很要命的账：这 32 遍扫的是同一个 16GB 文件，累计读取 512GB。真正的瓶颈是磁盘，不是 CPU。实测每遍扫 2.68 亿个数约 0.066 秒，换算到 40 亿个数大约每遍 1 秒，32 遍纯计算也就半分钟出头，而磁盘读 512GB 要慢得多。所以省遍数不是省计算，是省 I/O。

总结

这一页的全部做法都从同一句话出来：值域只有 232 个格子，个数只有 40 亿，格子数比个数多，就一定有空位。要回答范围问题，就把「格子」按需要切成位、切成 2 bit、切成 768 段，再和实际个数比。

位图是成本最低的一档，512MB 换一遍扫描；2 bit 计数账面上是 1024MB，差 24MB 装不进 1GB，分两趟把值域劈开就回到 512MB；3KB 时桶和位图都开不了，改成一遍粗分桶加桶内二分，把 32 遍压到 24 遍；只剩几个变量时老老实实二分 32 遍。

这套「数一数某一段里有多少个」的骨架还能顺着换成第 k 小、上中位数这类询问，改的是比较条件，不是框架。往后遇到「内存装不下但值域不大」的题，先算一遍值域和个数的账，思路基本就定了。
