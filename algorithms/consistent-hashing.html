一致性哈希：机器进出只搬一段

用 key 对机器数取余决定数据放哪台机器，加一台机器就要搬走九成数据。一致性哈希把哈希值排成一个环，机器进环、数据顺时针找第一个机器，增减机器只影响环上的一段弧。这一页把迁移比例、负载倾斜和虚拟节点都量一遍。

零、加一台机器要搬多少

10 台机器加 1 台，取模方案要搬走 90.93% 的 key。换成一致性哈希，搬走 9.38%，接近理论上的 1/11。

差别出在结构上：取模方案里「落在哪台机器」由 key 除以机器数的余数决定，机器数一改，几乎所有 key 的余数都变了。

一、取模方案的弱点

最简单的分布式存储是这样安排的：数据根据 key 决定存到哪台机器，机器一共 N 台，落在 key % N 号机器上。查询时用同一个公式算出机器号，找过去就行。

这个方案在机器数不变时很完美。麻烦出在「机器数会变」这件事上：扩一台、挂一台、换一台，N 都变了，所有 key 的落点都要重算。

变化位置不变的 key需要搬走的 key
10 台 → 11 台9.07%90.93%
10 台 → 9 台10.03%89.97%

具体来说，只有那些「原余数和现余数恰好相同」的 key 才不动，这个概率约等于 1/(N+1)。其余九成的数据全要跨机器搬家，一台机器扩容引发的是一次全量迁移。

二、把哈希域弯成一个环

一致性哈希换个思路：先规定一个固定的哈希域，比如 32 位整数，取值从 0 到 232−1；把这个区间首尾相接画成一个环。机器和数据都用同一个哈希函数映射到这个环上。

每台机器在环上占一个点。数据进来时算出它的环上位置，从这个位置出发顺时针找，遇到的第一个机器点就是它的归属。

// 环上定位：把机器的哈希值排好序，找第一个不小于 key 的点
    vector<pair<u64, int>> pts;   // (环上位置, 机器号)
    sort(pts.begin(), pts.end());

    int locate(u64 key) {
        auto it = lower_bound(pts.begin(), pts.end(), make_pair(key, -1));
        if (it == pts.end()) it = pts.begin();   // 绕回环头
        return it->second;
    }

环上定位是一次二分查找，不需要遍历所有机器。数据落在哪个点由「它顺时针方向的第一个机器点」唯一确定，与机器总数无关，这是它和取模方案最大的区别。

三、增减机器只动一段弧

加一台机器时，新机器点插进环里，只有「从新点出发逆时针到上一个机器点」这一段弧上的数据会改投它，其余数据完全不动。平均算下来，N 台机器加入第 N+1 台，搬走的比例是 1/(N+1)。

10 台机器上的 100 万个 key，实测三档虚拟节点数：

每台机器的虚拟节点数10 台 → 11 台搬走10 台 → 9 台搬走
10.28%9.54%
1009.38%10.74%
10008.63%9.76%

虚拟节点多的时候，迁移比例稳定在 1/11 附近。只有 1 个虚拟节点那一行的 0.28% 看着更漂亮，其实是个警告：新机器恰好落进一段很窄的弧，只接到 0.28% 的数据。它省下了迁移量，也意味着这台新机器几乎分不到活。负载倾斜的问题在下一节。

四、虚拟节点

机器数少的时候，环上只有那么几个点，落在相邻两个机器点之间的弧度大小差别很大，有的机器负责很宽的一段、有的很窄。数据按位置均匀铺满环，就变成了机器之间负载严重不均。

解决办法是让一台机器在环上占多个点：对每台机器编出若干虚拟节点，每个虚拟节点用不同的名字算哈希，散落在环上各处。数据归属仍然是「顺时针第一个点」，但一台机器拥有了很多段弧，总长度自然被摊平。

// 虚拟节点：一台机器在环上放 v 个点，一台机器的负载就摊平了
    void addNode(int id, const string& name, int vnodes) {
        for (int v = 0; v < vnodes; v++)
            pts.push_back({md5_64(name + "#" + to_string(v)), id});
    }

只有 1 个虚拟节点时，最多的机器扛了 7.55% 的数据，最少的只有 0.05%，差了 150 倍。加到 1000 个虚拟节点，极差收到 0.27%，标准差只占平均值的 3%。

虚拟节点带来两个附带好处：负载可以在机器之间手动调配（想给某台机器减负，就少给它几个虚拟节点），扩容时新机器也能立刻均匀接活，不用等它自然接满。代价是环上的点数变成「机器数 × 虚拟节点数」，定位要做的那次二分多花 log 倍的时间，实测 25000 个点的环上定位一次只要 0.053 微秒。

五、一台机器挂掉

减机器和加机器是对称的。50 台机器、每台 200 个虚拟节点，第 3 台退出后，实测 1.90% 的 key 换了位置，正好是它原来负责的份额。

这些 key 全被它的后继接走，但因为每个虚拟节点的后继各不相同，压力实际上摊到了 49 台机器上，最重的一台只多接了 0.11% 的 key。虚拟节点少的时候就不是这样了：一台机器挂掉，它的后继可能要一次性接过一大段弧，变成新的瓶颈。

六、哈希 key 怎么选

一致性哈希的均匀性依赖一个前提：机器点和数据点都要在环上散得开。机器名一般用「机器编号 + 虚拟节点序号」拼出来算哈希，这些名字互相独立，散得开。

数据这一侧的 key 要自己挑。挑的原则是「不同的数据得到不同且零散的位置」，所以要用会增加信息量的字段组合。拿用户维度的数据举例，用 user_id 参一个随机种子或时间片，就比用自增的 id 稳；用一段可能被截断的文本当 key，也比用它的前几个字节好。

反例是「key 的取值集中在一个小范围」。比如把一天的数据都按同一个日期字符串当 key，那它们全落在一个点上，虚拟节点再多也摊不开。环的均匀性靠的是输入本身的熵，这一点和哈希函数的均匀性是一回事。

环本身只存机器点，和数据量无关，所以数据涨到亿级也不会让定位变慢；25000 个点的环上定位一次 0.053 微秒。真正随数据量增长的是「算 key 的哈希」和「按结果把数据搬过去」这两件事，前者是 O(key 长度)，后者是扩容时的一次性开销。

总结

取模方案在机器数变化时要重算所有 key 的落点，10 台加 1 台搬走 90.93%。一致性哈希把哈希域弯成环，机器和数据都落在这个环上，数据顺时针找第一个机器点，加一台机器只搬走它接管的那段弧。

迁移比例的理论值是 1/(N+1)，实测虚拟节点够多时是 9.38%，与 1/11 吻合。只有 1 个虚拟节点时搬走 0.28%，省的是迁移量，换来的是一台机器几乎分不到数据。

虚拟节点解决负载倾斜：50 台机器、1 个虚拟节点时份额从 0.05% 到 7.55%，加到 1000 个虚拟节点后极差只剩 0.27%。机器挂掉时压力也会被多个后继分摊，实测第 3 台退出只影响 1.90% 的 key，最重的一台多接 0.11%。定位是一次二分，代价 O(log V)，环的空间与数据量无关。
