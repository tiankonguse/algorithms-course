格子上的三维动态规划：骑士概率与整除路径

前两维是位置，第三维跟位置无关。骑士那道题里第三维是「还剩几步要走」，整除路径那道题里第三维是「累加和对 k 取模的余数」。位置两维好理解，多出来的这一维才是这类题的难点：它得能把「前面走过的路对后面的影响」全部装进去，装不完就改不成动态规划。这一页把两道题的递推、依赖方向和空间压缩都过一遍。

零、位置之外的那一维，装的是什么

两维格子上做动态规划，状态 (i, j) 说清楚了「走到哪」。一旦路径上还带着别的信息，两维就不够用了：骑士的路径长度是规定好的，所以真正要记的是「还剩几步」；整除路径只关心整个路径的和对 k 取模的结果，所以真正要记的是「当前余数」。

判断第三维要找什么，办法是问一句：把 (i, j) 定死之后，还需要知道什么才能唯一确定答案？答案里出现过的那个量，就是第三维。

一、骑士在棋盘上的概率

n × n 的棋盘，骑士从 (row, col) 出发，每次在八种走法里等概率挑一个走过去，一共走 k 步，中间任何一步踩出棋盘就出局。问走完 k 步还留在棋盘上的概率。

定义 f(n, i, j, k)：从 (i, j) 出发还有 k 步要走，返回最后留在棋盘上的概率。三个可变参数齐了，答案就定了，跟你是怎么走到 (i, j) 的无关。

// 骑士的八种走法
    int dx[8] = {-2, -1, 1, 2, 2, 1, -1, -2};
    int dy[8] = {1, 2, 2, 1, -1, -2, -2, -1};

    // 从 (i, j) 出发还有 k 步要走，返回最后留在棋盘上的概率
    double f(int n, int i, int j, int k, vector<vector<vector<double>>>& dp) {
        if (i < 0 || i >= n || j < 0 || j >= n) {
            return 0;
        }
        if (dp[i][j][k] >= 0) {
            return dp[i][j][k];
        }
        double ans = 0;
        if (k == 0) {
            ans = 1;
        } else {
            for (int d = 0; d < 8; d++) {
                ans += f(n, i + dx[d], j + dy[d], k - 1, dp) / 8;
            }
        }
        return dp[i][j][k] = ans;
    }

越界的格子直接返回 0，因为它已经出局了；k == 0 时返回 1，因为一步都不用走，只要还站在棋盘上就是成功。剩下的情况把八个方向各走一步的结果平均一下。

这份递归不记忆化的话是按 8^k 长的：k = 0 是 1 条路，k = 5 是 32768 条，k = 6 是 262144 条。而状态只有 n² (k+1) 个，n = 8、k = 5 时也才 384 个，重复率高得离谱。

二、换个方向写：走 t 步之后落在哪里

把「还剩几步」翻成「已经走了几步」，递推就顺过来了：cur[i][j] 表示走 t 步之后落在 (i, j) 的概率，从起点概率 1 开始，每一步把当前所有非零格子按 1/8 推给八个邻居，出界的直接丢掉。

// 反过来记「走了 t 步之后落在每个格子上的概率」，只需要两层
    double knightProbability(int n, int k, int row, int col) {
        vector<vector<double>> cur(n, vector<double>(n, 0));
        cur[row][col] = 1;
        for (int t = 0; t < k; t++) {
            vector<vector<double>> nxt(n, vector<double>(n, 0));
            for (int i = 0; i < n; i++) {
                for (int j = 0; j < n; j++) {
                    if (cur[i][j] == 0) {
                        continue;
                    }
                    for (int d = 0; d < 8; d++) {
                        int x = i + dx[d], y = j + dy[d];
                        if (x >= 0 && x < n && y >= 0 && y < n) {
                            nxt[x][y] += cur[i][j] / 8;
                        }
                    }
                }
            }
            cur.swap(nxt);
        }
        double ans = 0;
        for (int i = 0; i < n; i++) {
            for (int j = 0; j < n; j++) {
                ans += cur[i][j];
            }
        }
        return ans;
    }

这个写法天然只需要两层：算第 t+1 层只读第 t 层。整张 n × n × (k+1) 的表用不上，两组 n × n 换着用就够了。

实测 n = 25、k = 100：三维表算 0.69 ms，两层滚动算 0.36 ms；内存从 493.2 KiB 降到 9.8 KiB。这里时间也快了将近一倍，原因是一样的：9.8 KiB 全程躺在缓存里。

两个版本的答案完全一致，n = 3、k = 2、起点 (0, 0) 都是 0.0625。这个数是 1/16，刚好是「两步全都落在棋盘上」的那一条路径的概率：从 (0,0) 只有两条路走第一步，第二步各自出界的概率是 1/2，乘起来就是 1/16。

三、整除路径：第三维是余数

给一个 n 行 m 列的整数矩阵和一个整数 k，从 (0, 0) 走到 (n−1, m−1)，每次只能向下或向右，问路径和能被 k 整除的路径有多少条。

如果只记 (i, j)，走到同一个格子时累加和可能不一样，答案也就不一样。把「从 (i, j) 出发继续走到终点、凑出余数 r 的路径数」定义成状态，三个参数就齐了。

// 从 (i, j) 走到右下角，路上累加和 % k 的余数是 r，有多少条路径
    int f2(vector<vector<int>>& grid, int n, int m, int k, int i, int j, int r,
           vector<vector<vector<int>>>& dp) {
        if (i == n - 1 && j == m - 1) {
            return grid[i][j] % k == r ? 1 : 0;
        }
        if (dp[i][j][r] != -1) {
            return dp[i][j][r];
        }
        // 从 (i, j) 出发，后面需要凑出来的余数
        int need = (k + r - grid[i][j] % k) % k;
        long long ans = 0;
        if (i + 1 < n) {
            ans = f2(grid, n, m, k, i + 1, j, need, dp);
        }
        if (j + 1 < m) {
            ans = (ans + f2(grid, n, m, k, i, j + 1, need, dp)) % MOD;
        }
        return dp[i][j][r] = ans;
    }

这一步走出 (i, j) 之后，剩下的路需要凑出的余数变了：本格的余数是 grid[i][j] % k，想凑出 r，后面就得凑出 (k + r − grid%k) % k。多加一个 k 再取模是为了让结果落在 0 到 k−1，别写出负数下标。

递归出口在最右下角：走到终点时只剩最后一格要收，grid[n−1][m−1] % k 等于 r 就算一条合法路径。

四、从右下角往左上角填，再压掉一行

把依赖画清楚：dp[i][j][r] 只读 dp[i+1][j][need] 和 dp[i][j+1][need]，一个在下面、一个在右面。所以填表顺序是从右下角开始，行从下往上、列从右往左。

// 严格位置依赖，从右下角往左上角填
    int numberOfPaths3(vector<vector<int>>& grid, int k) {
        int n = grid.size(), m = grid[0].size();
        vector<vector<vector<int>>> dp(n, vector<vector<int>>(m, vector<int>(k, 0)));
        dp[n - 1][m - 1][grid[n - 1][m - 1] % k] = 1;
        for (int i = n - 2; i >= 0; i--) {
            for (int r = 0; r < k; r++) {
                dp[i][m - 1][r] = dp[i + 1][m - 1][(k + r - grid[i][m - 1] % k) % k];
            }
        }
        for (int j = m - 2; j >= 0; j--) {
            for (int r = 0; r < k; r++) {
                dp[n - 1][j][r] = dp[n - 1][j + 1][(k + r - grid[n - 1][j] % k) % k];
            }
        }
        for (int i = n - 2; i >= 0; i--) {
            for (int j = m - 2; j >= 0; j--) {
                for (int r = 0; r < k; r++) {
                    int need = (k + r - grid[i][j] % k) % k;
                    dp[i][j][r] = dp[i + 1][j][need];
                    dp[i][j][r] = (dp[i][j][r] + dp[i][j + 1][need]) % MOD;
                }
            }
        }
        return dp[0][0][0];
    }

    // 空间压缩：只需要「下面那一行」，从最后一行往上滚
    int numberOfPaths4(vector<vector<int>>& grid, int k) {
        int n = grid.size(), m = grid[0].size();
        vector<vector<int>> below(m, vector<int>(k, 0));
        for (int i = n - 1; i >= 0; i--) {
            vector<vector<int>> cur(m, vector<int>(k, 0));
            for (int j = m - 1; j >= 0; j--) {
                if (i == n - 1 && j == m - 1) {
                    cur[j][grid[i][j] % k] = 1;
                    continue;
                }
                for (int r = 0; r < k; r++) {
                    int need = (k + r - grid[i][j] % k) % k;
                    long long v = 0;
                    if (i + 1 < n) {
                        v += below[j][need];
                    }
                    if (j + 1 < m) {
                        v += cur[j + 1][need];
                    }
                    cur[j][r] = v % MOD;
                }
            }
            below.swap(cur);
        }
        return below[0][0];
    }

压掉 i 这一维之后，表里只剩「下面那一行」和「正在写的这一行」。注意别在每一行开头重新申请一块临时表：那样每行都要分配一次 m × k 的连续内存，实测反而慢，200 × 250、k = 100 时 9.4 ms；把两块缓冲区换着用是 8.0 ms。三维表本身是 10.6 ms。

这题的空间差距最大：三维表 n × m × k，200 × 250、k = 100 时是 500 万个 int，19.1 MiB；压成一行之后是 2 × m × k 个 int，195.3 KiB，差 100 倍。

演示二：整除路径从右下角开始，逐格填出整张余数表

五、两道题的第三维长得不一样

骑士的第三维是步数，取值范围 0 到 k，一共 k+1 种；整除路径的第三维是余数，取值范围 0 到 k−1，一共 k 种。两者都是「一个不超过 100 的小整数」，所以表都能开得下。

更要紧的差别在依赖方向。骑士的第三维只依赖 k−1 那一层，方向单一；整除路径的第三维在同一层里互相跳（r 读 need，need 又是另一个余数），所以那一维不能压，只能整体留着。压缩能压掉哪一维，取决于哪一维满足「本层只读上一层」。

六、复杂度分析

骑士那两维位置再加上步数，表和格子的规模是一个量级；整除路径多出来的余数维是 k ≤ 100，而格子总数被约束在 5 万以内，所以 n · m · k 最大也就 500 万，恰好卡在能跑完的边界上。

七、总结

位置两维之外要不要第三维，取决于「把位置定死之后，答案还能不能唯一确定」。骑士需要知道还剩几步，整除路径需要知道当前余数，这两个量就是各自的第三维。

改法和前面几步一样，但这里多了一个新东西：递推方向可以换。骑士那道题把「还剩几步」翻成「已经走了几步」之后，状态变成了按步数往前推，两层滚动顺手就出来了。

压缩只针对「本层只读上一层」的那一维。余数维在同一层里互相引用，压不得；步数维方向单一，压得掉。另外压缩的时候记得让缓冲区别每轮重新申请，实测这一处能差出十几个百分点。
