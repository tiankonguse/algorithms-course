对数器

没有在线评测的时候，怎么确认自己写的那份代码是对的？找一个「慢但一定对」的程序陪跑，随机喂同样的数据，把两边的结果对着比。

零、背景

练算法的人迟早会撞上这三件事。

  • 网上看到一道题，想了半天觉得会做了，可它没有任何地方能提交
  • 和朋友讨论一个做法，两个人说的都有道理，谁也说服不了谁
  • 笔试里前面几个小样例都过了，忽然来一个巨大数据量就报错，大到你根本没法用眼睛找是哪一组数据出的问题

第三件最要命。样例大到几万个数，报错信息只告诉你「答案错误」，连是哪个例子都不说。这时候需要的不是更好的眼睛，是一个能替你自动造小例子、自动比对的装置。

这个装置叫对数器。它不聪明，也不优雅，但它是唯一能在没有评测机的情况下给出「我这份代码应该是对的」这种判断的办法。

一、五样东西

搭一个对数器需要凑齐五样东西，缺一件就跑不起来。

  1. 方法 a：你要验证的那个方法，也就是你自认为的最优解
  2. 方法 b：实现复杂度不好，但是容易写对、几乎不可能写错的方法
  3. 随机样本产生器：长度也随机、值也随机
  4. 把 a 和 b 跑在相同的输入样本上，比对得到的结果
  5. 如果有一个样本让两边对不上，把这个样本打印出来，人工干预

前四步都机械，第五步才是关键。它交给你的不是一句「错了」，而是一个能复现错误的具体输入，而且往往是长度很小的输入。

有了这个小样本，剩下的就是熟活：把它贴进代码里单步走，或者在几个位置加打印，看第一次偏离是在哪一步发生的。

二、随机样本产生器

产生器要做的事只有一句：长度随机，每个值也在给定范围里等概率随机。等概率这三个字不是修辞，它决定了对数器能不能覆盖到那些「特别」的数据。

值是怎么来的，值得一步步拆开看。

四步里每一步都保住等概率：[0,1) 上均匀，乘 v 之后在 [0,v) 上仍然均匀，强转截断把区间切成 v 段等长的段，加 1 只是整体平移。

实测一下这个说法：取 v = 6，投 12 万次，每个桶的期望是 20000，实测最大相对偏差 0.45%。偏差来自随机本身，不是写法。

产生器有两个参数要自己定：N 是长度上界，V 是值域。长度也要随机，写成 n = rand() % N 而不是固定值，这样 n = 0 和 n = 1 这两种边界会被自动覆盖到，它们恰恰是最容易写错的地方。

// 随机样本产生器：长度 n，每个值等概率落在 1~v
    vector<int> randomArray(int n, int v) {
        vector<int> arr(n);
        for (int i = 0; i < n; i++) {
            // rand01() 返回 [0, 1) 上的一个随机小数
            arr[i] = (int)(rand01() * v) + 1;
        }
        return arr;
    }

    // 每个方法都要拿到原始样本的一份拷贝
    vector<int> copyArray(const vector<int>& arr) {
        vector<int> ans(arr.size());
        for (int i = 0; i < (int)arr.size(); i++) {
            ans[i] = arr[i];
        }
        return ans;
    }

这里有个看着多余其实不能省的函数：copyArray。方法 a 大多是原地排序，排完 arr 已经有序了；方法 b 如果拿这份排好的数组去排，结果当然一致，对数器就变成了永远说「通过」的摆设。每个方法都要拿到原始样本的一份拷贝。

三、一份能跑起来的对数器

把上一节的产生器和比对函数拼起来，就是一个完整的对数器。要验证的方法 a 是插入排序，方法 b 直接用语言自带的排序，自带排序不用你写，也就没有写错的机会，这是最省事的 b。

bool sameArray(const vector<int>& a, const vector<int>& b) {
        if (a.size() != b.size()) {
            return false;
        }
        for (int i = 0; i < (int)a.size(); i++) {
            if (a[i] != b[i]) {
                return false;
            }
        }
        return true;
    }

    int main() {
        int N = 200;          // 随机样本的长度上界
        int V = 1000;         // 随机值落在 1 ~ V
        int testTimes = 50000;
        for (int i = 0; i < testTimes; i++) {
            int n = rand() % N;                 // 长度也随机，0 和 1 会被自动覆盖到
            vector<int> arr = randomArray(n, V);
            vector<int> a = copyArray(arr);     // 方法 a：想验证的那个
            vector<int> b = copyArray(arr);     // 方法 b：笨，但一定对
            insertionSort(a);
            sort(b.begin(), b.end());
            if (!sameArray(a, b)) {
                printArray(arr);                // 打印这个出错的样本，带着它去 debug
                return 0;
            }
        }
        cout << "测试通过" << endl;
        return 0;
    }

循环里那句 printArray(arr) 打印的是出错样本，不是排完的结果。你要带着原始输入去 debug，排完的结果只能告诉你「错了」。

上一讲的三种排序也常反过来用：它们足够笨、足够短，拿来当方法 b 验证别的东西正好。选择、冒泡、插入排序那一页里的三个函数可以直接抄过来。

四、出了错之后

先说一个容易被低估的事实：一轮是不够的。把四种常见笔误分别注入方法 a，用同一台对数器去抓，结果是这样的。

注入的笔误50000 轮内抓到首轮命中，中位数最差
冒泡少跑最后一趟（end > 1）200 / 20032 轮316 轮
插入到不了 0 号位（j > 0）200 / 2001 轮2 轮
选择的初值写成 n-1200 / 2001 轮2 轮
选择多写一个等号（<=）0 / 200抓不到—

四种笔误长这样，改动都只有一两个字符。

// bug 1：最后一个 end 没跑，只有前两个数需要交换时才现形
    for (int end = n - 1; end > 1; end--) {          // 原版：end > 0

    // bug 2：0 号位置永远参与不了
        for (int j = i - 1; j > 0 && arr[j] > arr[j + 1]; j--) {   // 原版：j >= 0

    // bug 3：minIndex 的初值写成了最后一个下标
        int minIndex = n - 1;                        // 原版：int minIndex = i;

    // bug 4：多写了一个等号，只丢稳定性，排出来的结果仍然正确
            if (arr[j] <= arr[minIndex]) {           // 原版：arr[j] < arr[minIndex]

第一行那个「最差 316 轮」值得看一眼。同一个 bug，运气好的时候第一轮就撞上，运气差的时候要跑三百多轮。所以 testTimes 别写 10 就收工，几千几万轮也就是几秒钟的事。

抓到样本之后，如果它还是有点长，可以再把它缩小一轮：试着删掉一个元素，用剩下的重跑，如果仍然错就保留这次删除，否则换下一个位置试。几趟下来往往能从几十个元素缩到三五个。

缩到最小之后再进调试器，需要盯的位置就少多了。这一步没有通用代码可抄，手动删几次比写个自动缩小器快。

五、抓不到的那些

表格最后一行是重点：多写一个等号，50000 轮一轮都没抓到。原因是这个改动只破坏稳定性，排出来的数组作为多重集仍然正确。对数器比的是输出，输出没变它就什么都看不见。

所以「对数器跑了几万轮全过」这句话的准确含义是：在你随机的那批数据上，方法 a 和方法 b 的输出一致。它不是证明，只是没找到反例。

另一件会拖后腿的事是值域 V 定得太大。有些 bug 只在样本里存在相等元素时才现形，而 V 一大，随机样本里出现重复值的概率就陡降。n = 10 时实测：V = 5 是 100%，V = 50 掉到 62%，V = 1000 只剩 4.35%。

用一个真实的例子量一下后果：把一个二分查找里的 a[mid] >= x 写成 a[mid] > x，这个 bug 只在数组里有和 x 相等的元素时才现形。对数器的其它参数不动，只改 V。

演示：值域 V 对「多久能抓到」的影响

50 轮

柱高用的是对数刻度，柱顶标的是首轮命中的中位数（2000 次独立实验）。V = 10 时两轮就有一半把握，V = 1000 时要 148 轮，如果你的对数器只跑 50 轮，那这个 bug 有接近八成的概率从眼皮底下溜走。

反过来用这条规律：想让对数器更容易抓到东西，就把值域压小、把长度压小。小样本不是偷懒，是刻意的取样策略。

六、复杂度分析

对数器本身不是算法，但它的代价是可以算的。设方法 a 的复杂度是 O(f(n))，方法 b 是 O(g(n))，跑 T 轮。

环节时间额外空间
生成一个长度 n 的样本O(n)O(n)
方法 b（自带排序 / 暴力枚举）O(g(n))O(n)
方法 a（待验证）O(f(n))视实现而定
比对两个结果O(n)O(1)
完整 T 轮O(T · (f(n) + g(n)))O(n)

空间上很省：每轮只需要原始样本加上两到三份拷贝，都是 O(n)，跑完一轮就回收。真正花钱的是时间，因为 T 是乘在外面的。

轮数该怎么定，也有个模型。设单个样本能触发这个 bug 的概率是 p，那 T 轮里至少抓到一次的概率是 1 - (1-p)^T，期望要跑 1/p 轮。前面那 316 轮的最差情况，对应的就是一个不算小的 1/p。这也是为什么 T 往大里写几乎总是划算的：它是线性的代价，换的是指数下降的漏网概率。

最后

对数器的门槛其实不在代码，在于你得把同一件事用两种思路各写一遍，一个笨，一个想快。想快那个写错了才有得验证，笨那个写错了只会让整个装置一起骗你。

所以方法 b 尽量挑那种「照着定义直接翻译」的写法，或者干脆用语言自带的排序、自带的容器。它慢一点没关系，它错不起。

后面几乎所有题目都能这么验，尤其适合验贪心和观察出来的规律，那两类东西最容易出现「样例全过，大数据就崩」。这一讲只是拿排序举了个最简单的例子。
