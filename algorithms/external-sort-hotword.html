10G 的文件、5G 的内存

一个 10G 的文件，里面全是 32 位无符号整数，无序，给你 5G 内存，要求产出另一个 10G 的文件装下排好序的结果。内存比文件小，这一条就直接否掉了「读进来排序写回去」。后面半页换一道题：一天 100 亿条搜索词，要求任何时刻都能立刻说出当天的 Top100 高频词。两道题看着无关，都走同一条路：把数据切开，让每一份都小到能装进内存。

零、内存装不下，就把文件切开

读不完整个文件，不等于做不了排序。排序能拆：把文件切成 k 块，每块单独排好序落盘，得到 k 个有序的小文件；再把 k 个有序文件合并成一个大文件，合并这一步只需要同时盯着 k 个文件的队头。

10G 的文件、5G 内存，按每块 3G 算，切 4 块就够，每块排完写回磁盘。接着做 4 路归并，读缓冲和写缓冲各留几百 MB，5G 的内存还剩一大截。

真正的约束在磁盘上：临时文件要额外的 10G 空间，加上输入 10G、输出 10G，一次性要 30G 可用空间。这是外部排序绕不过去的成本，方案设计时要先说清楚。

一、切块加归并，实测一遍

把规模按比例缩到能在一台机器上跑完：2500 万个 32 位整数（100MB），内存上限卡在 200 万个元素（8MB），也就是每块只能装下文件的 1/13。

// 内存装不下整个文件：先切成能装下的块，块内排好序落盘，再做 K 路归并
    vector<u32> buf(M);                      // M 是内存能装下的元素个数
    int blocks = 0;
    while (true) {                           // 第一趟：分块排序
        size_t got = fread(buf.data(), 4, M, in);
        if (!got) break;
        sort(buf.begin(), buf.begin() + got);
        FILE* out = fopen(tmpName(blocks++).c_str(), "wb");
        fwrite(buf.data(), 4, got, out);
        fclose(out);
    }
    vector<FILE*> fs(blocks);
    priority_queue<pair<u32,int>, vector<pair<u32,int>>, greater<>> pq;
    for (int i = 0; i < blocks; i++) {       // 第二趟：小根堆挑最小的队头
        fs[i] = fopen(tmpName(i).c_str(), "rb");
        u32 v; fread(&v, 4, 1, fs[i]);
        pq.push({v, i});
    }
    while (!pq.empty()) {
        auto [v, i] = pq.top(); pq.pop();
        fwrite(&v, 4, 1, out);
        if (fread(&v, 4, 1, fs[i]) == 1) pq.push({v, i});
    }

实测结果：分成 13 块，分块排序加写临时文件 1.27 秒，13 路归并 1.14 秒，合计 2.40 秒。校验输出 2500 万个整数，全序成立，而且和「把输入直接排一遍」的结果逐元素相同。

把内存上限压到 8MB，块数涨到 13，归并的路数也跟着涨到 13。归并路数不是越多越好：每一路都要占一个读缓冲，100 路归并就要 100 份缓冲，内存再大也经不住这么分。工程上常用分层归并，先合并成若干中等大小的有序段，再合并成最终结果。

二、值域小的时候，直接分桶更快

上一节的思路适用于任意数据，代价是数据前后要读写两轮。32 位整数有一个额外的好处：值域只有 232，可以按高位直接分桶，跳过「排序」这一步。

做法是两遍扫描。第一遍只数数：按最高 12 位分成 4096 个桶，统计每个桶里有多少个数，顺带算出每个桶在输出文件里的起始偏移。第二遍再扫输入，读到一个数就按它的高 12 位算出所属的桶，用带缓冲的随机写追加到输出文件的对应位置。两遍扫完，数据已经按桶分好了段，每个桶内部还是乱的。

第三步逐桶处理：把一个桶的全部元素读进内存排序，写回原位。桶里最多装多少个元素，就是第三步需要的内存。4096 个桶、2500 万个数，平均每桶 6103 个，实测最大的一桶 6363 个，也就是 25KB。

实测：定位加落盘 1.35 秒，逐桶排序 0.79 秒，合计 2.14 秒，比 13 路归并的 2.40 秒还快一点。更关键的是，整个过程只打开一个输入文件和一个输出文件，内存需求由「最大的桶」决定，和文件总大小无关。

代价是随机写。分桶落盘时每个数都要写到文件的某个位置，顺序写变成了跳着写，机械硬盘上会慢很多；换成 SSD 或者先把每个桶攒在缓冲里批量写，这条路才划算。所以两种做法的取舍很清楚：值域小、盘快，用分桶；值域大或者盘是机械的，用切块归并。

三、100 亿条搜索词，随时问 Top100

第二道题的形状完全不同：数据是一天里陆续到来的搜索词，每条不超过 64 字节，要求每天 0 点清零重新统计，而且任何时刻都要能立刻回答当前的 Top100。

先算规模。100 亿条 × 64 字节 = 640GB，超过单机内存几个数量级。但真正占内存的不是原始数据条数，是「有多少个不同的词」：词频统计要存的是每个词和它的计数。

精确做法是哈希分片。按词的哈希值模 M 把所有数据分到 M 片，每一片自己维护一张哈希表，同时维护一个大小为 100 的小根堆（堆顶是当前第 100 名，来一个更大的就替换）。查询时把 M 个堆的堆顶候选合并，再取前 100。分片保证同一个词一定落在同一片，计数不会漏也不会重；分片到多台机器上就是横向扩展。

用缩小版数据把内存账摸清楚：词典 100 万个词、按 Zipf 分布发 1000 万条搜索，实际出现过的词 76.4 万个。单存这 76 万个词的计数就要 6MB，加上词本身（平均几十字节）和哈希表的槽位，实际占用 40MB 上下。真实规模下词典可能上亿，这一项就涨到几十 GB，单机放不下，分片是必选项。

四、只留 k 个计数器：k 该开多大

分片解决的是「装不下」，代价是要多台机器。如果允许结果有一点点误差，还有一种只用固定内存的做法。

思路是只保留 k 个计数器：来一个已经在表里的词，计数加一；来一个不在表里的词，如果表没满就新建一条；表满了就找出计数最小的那条，把它删掉，让新词继承它的计数再加一。计数最小的那条一定是最不像高频词的，牺牲它换一个可能更热的候选。这就是 SpaceSaving。

// Top-K 只留 k 个计数器：来一个新词就顶掉当前计数最小的那个（计数继承过来再 +1）
    unordered_map<string, ll> cnt;
    priority_queue<pair<ll, string>, vector<pair<ll, string>>, greater<>> pq;
    for (const string& w : stream) {
        auto it = cnt.find(w);
        if (it != cnt.end()) { it->second++; pq.push({it->second, w}); continue; }
        if ((int)cnt.size() < k) { cnt[w] = 1; pq.push({1, w}); continue; }
        ll c0 = 0;
        while (!pq.empty()) {                 // 堆顶可能已经过期，惰性删
            auto [c, x] = pq.top();
            auto f = cnt.find(x);
            if (f != cnt.end() && f->second == c) { c0 = c; cnt.erase(f); break; }
            pq.pop();
        }
        cnt[w] = c0 + 1;                      // 顶掉的计数当成自己的底子，再 +1
        pq.push({cnt[w], w});
    }

这样得到的计数只会偏大：一个词要是被顶掉过又回来，它会继承那次顶替时最小计数器的值，等于把别人的票也认领了。偏差有上界，任何词的估计值不会比真实值多超过 N/k，而表里最小的那个计数器就是这个上界的实时读数。反过来，真实频率超过 N/k 的词一定会留在表里。

这条界线可以直接拿来做决策。上面那份数据里，真实 Top100 的第 100 名是 6959 次，而 k = 100 时 N/k = 107/100 = 100000，比它大了 14 倍，所以这一档按定理不保证留得住第 100 名。要保证 Top100 全中，需要 k × 6959 > 107，也就是 k 至少 1437。实测两条曲线一左一右夹住了这个数：

三处细节值得留意。真实词表里只出现过 763765 个不同的词，k = 106 的表压根没被填满，一次顶替都没发生，所以最大高估量是 0。倒数第二列每一行都恰好等于表里最小的那个计数器，这不是巧合：每一次顶替都把最小计数当成新词的底子，所以高估量由最小计数器直接量出来。至于 k ≥ 1437 这条线，它只是充分条件。k = 1000 时召回已经满格（真实 Top100 一个不少地留在表里），而输出 Top100 的精度要到 k = 1500 才满，理论界正好落在 1000 和 1500 中间。

k = 100 那一档是个反面教材：只有 24 个词对得上，而且进表的那些词被反复顶替，估计值虚高到真实值的 140%。表里另外 76 条词的真实排名从 136 名散到 72 万名，中位数在 17603 名，多数是长尾里排不上号的词，是它们挤掉了真正该上榜的那些。k 涨到 10000，召回精度都满格，内存只要 0.4MB。用几 MB 换掉「词典规模」这个无底洞，这是 SpaceSaving 最值钱的地方。

代价是 k 不能凭感觉挑。k 取小了，Top100 抓不全；取大了，内存和每次更新找最小值的开销都会涨上来。工程上先估一个 f100 的量级（第 100 名大约多少条），再用 k ≈ N / f100 定表的大小，这是最直接的办法。

四个方案的空间项写法不一样，值得对着看。切块归并的空间是 O(N/k)，k 是自己选的块数；分桶排序的空间是 O(max mi)，取决于数据在桶里怎么分布，最坏情况下所有数据挤进一个桶，这条路就退化成分桶加单块排序；分片统计的空间随「不同词数」走，和数据总量无关；SpaceSaving 的空间只跟 k 有关。

时间上，外部排序的常数全在 I/O 上。实测 100MB 的数据切 13 块，纯 CPU 的排序和归并加起来 2.4 秒，而真实场景下 10G 的文件光读一遍就要几十秒。所有「外部」方案的第一优化目标都是少读少写，不是少比较。

总结

两道题的共同点是把数据切开：排序题按「内存能装多少」切块，切完再归并；统计题按「词的哈希」分片，分片保证同一个词不会漏也不会重。

切块归并的通用性最好，代价是四遍数据量的读写和一份等大的临时磁盘；值域是 32 位这种小空间时，按高位分桶能把读写压到三遍，内存只由最大的桶决定，实测 2.14 秒比 13 路归并的 2.40 秒还快。

Top-K 那半页给出了一个可以量化选择的办法：精确分片的空间随不同词数走，装不下就得上机器；SpaceSaving 只用 k 个计数器，k 由「第 K 名的频率」反推出来，实测 k=1437 是这条数据的临界值，取 10000 就能全中而且只占 0.4MB。

需要「绝不漏掉任何一个候选」时用分片精确统计；允许近似、但要固定内存时用 SpaceSaving；两者也可以叠起来：先用 SpaceSaving 筛出候选，再对候选做一遍精确计数。
