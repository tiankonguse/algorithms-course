方案本身也要最优：字典序最小的两个例子

有些题只要交出任意一个达到最优值的方案就够了。这一页的两题还额外规定：最优值并列时，方案本身要字典序最小。第一题靠 dp 值直接定位答案的每一位，第二题得把方案跟着 dp 值一起存下来。

零、两个问题

第一个：给数组 arr，输出它的最长递增子序列，有多个答案时输出字典序最小的那个。这里的字典序是把每个数字看成一个单独的字符来比，比如 120 认为比 36 大，所以要求是「从左到右每一位都尽量小」。

第二个：n 个工具，每个有重量 a、阻力 b、能提升的停留时间 c。背包承重不超过 m，力气不超过 v，问最久能待多久，并返回下标字典序最小的选择方案。这里的字典序是把下标方案整体看成一个字符串，比如「1 120」比「1 2」小。

两个「字典序」的定义不一样，这个差别后面会专门讲。

一、先把「以 i 开头」算出来

最长递增子序列的常规 dp 是 dp[i] 表示「以 i 位置的数字结尾」的最长长度，从左往右做。但字典序最小要求的是「从左到右每一位尽量小」，得先知道「从 i 出发还能排多长」，于是改成从右往左做。

定义 dp[i] 为「必须以 nums[i] 开头的情况下，最长递增子序列的长度」。算它的时候维护一个辅助数组：ends[L-1] 是已经扫过的后缀里，长度为 L 的递增子序列的首元素最大能是多少。这个数组严格递减，所以能二分。

    
// dp[i] : 必须以 i 位置的数字开头的情况下，最长递增子序列长度
    // ends[L-1] : 后缀里长度为 L 的递增子序列，首元素最大能是多少，严格递减
    int bs(int len, int num) {                         // 找 <= num 的最左位置
        int l = 0, r = len - 1, m, ans = -1;
        while (l <= r) {
            m = (l + r) / 2;
            if (ends[m] <= num) { ans = m; r = m - 1; }
            else l = m + 1;
        }
        return ans;
    }
    int dp() {
        int len = 0;
        for (int i = n - 1; i >= 0; i--) {             // 从右往左，每个数当一次开头
            int find = bs(len, nums[i]);
            if (find == -1) { ends[len++] = nums[i]; dp[i] = len; }
            else { ends[find] = nums[i]; dp[i] = find + 1; }
        }
        return len;
    }

为什么是「首元素最大」：nums[i] 要能接在一条长度 L 的链前面，条件是 nums[i] < 那条链的首元素。同一长度下首元素越大，后面的数就越容易接上来，所以只留最大的那个就够了。

二分的写法是找 <= num 的最左位置。找不到（所有 ends 都比 num 大）说明 num 能接在所有已有链的前面，长度加一，追加到末尾；找到了就说明它能接到第 find 条链上，dp[i] = find + 1，同时把 ends[find] 更新成 num（num 比原来的值大，是这个长度下更优的首元素）。

二、dp 值直接给出答案位置

长度 k 出来之后，答案的每一位是确定的：一个 dp[i] = d 的位置，只能当答案里倒数第 d 个，也就是正数的第 k - d 位（下标从 0 起）。于是从左到右扫一遍数组，把每个数往它该去的位置上放。

    
// 从左到右扫一遍，dp[i] 直接决定 nums[i] 该落在答案的第几位
    k = dp();
    fill(ans, ans + k, INT_MAX);
    for (int i = 0; i < n; i++) {
        if (dp[i] == k) {
            ans[0] = nums[i];                          // 没有前一位，直接覆盖
        } else {
            if (ans[k - dp[i] - 1] < nums[i]) {        // 只跟前一位比，递增关系就接上了
                ans[k - dp[i]] = nums[i];
            }
        }
    }

两个地方值得停下来看。

第一个是 dp[i] == k 时为什么直接赋值不比较。因为答案的第一位没有前一位可比，而且同一个位置会有好几个候选：随机样本里第一位的候选平均有 2.82 个，57.13% 的样本第一位有多于一个候选。这里能直接覆盖，靠的是一条性质：如果 i < j 且 dp[i] == dp[j]，那么 nums[i] >= nums[j]。反过来想就明白了：要是 nums[i] < nums[j]，那 i 完全可以接在「以 j 开头的那条最长链」前面，dp[i] 至少是 dp[j] + 1，跟 dp[i] == dp[j] 矛盾。所以同一个位置的候选值随下标增大是不增的，一路覆盖下去最后留下的就是最小的那个。随机 2 万组、191 万对「同 dp 值」的组合实测，反例 0 个。

第二个是为什么只跟前一位比就够了。答案是按 i 从小到大填的，轮到 i 的时候它前面那一位早就定下来了，而后面那一位还没轮到。递增关系由「后一位填进来时检查它的前一位」来保证，不会漏。

四、潜水：dp 值存不下方案

第二题是二维费用的 0/1 背包。dp[j][k] 是「重量不超 j、阻力不超 k」的最久时间，转移是「不要 i 号工具」和「要 i 号工具」取大。到这里都跟普通的背包一样。

区别在于：时间相等的时候还要比方案，而方案是一个下标序列，它没法从 dp 值里反推出来（二维背包的状态里没有「第几个工具」这一维可走）。所以得给每个状态额外挂一个 path[j][k]，跟 dp 值同步更新。

    
// 空间压缩版：dp[j][k] 是「重量不超 j、阻力不超 k」的最大停留时间
    // path[j][k] 是达到这个时间、下标字典序最小的方案字符串
    for (int i = 1; i <= n; i++) {
        for (int j = m; j >= a[i]; j--) {              // 倒着走，保证读到的是 i-1 那一轮
            for (int k = v; k >= b[i]; k--) {
                string p2 = path[j - a[i]][k - b[i]].empty()
                          ? to_string(i)
                          : path[j - a[i]][k - b[i]] + " " + to_string(i);
                int val = dp[j - a[i]][k - b[i]] + c[i];
                if (dp[j][k] < val) {
                    dp[j][k] = val;
                    path[j][k] = p2;
                } else if (dp[j][k] == val) {          // 时间一样时比方案，字符串比较
                    if (p2 < path[j][k]) path[j][k] = p2;
                }
            }
        }
    }

内层两个循环都倒着走，这是 0/1 背包空间压缩的标准要求：这样读到的 dp[j-a[i]][k-b[i]] 还是上一轮（前 i-1 个工具）留下的值，不会被本轮刚写进去的结果污染。

五、字典序的两种读法

题面给的例子是「1 120」比「1 2」小。这是纯粹的字符串比较：前两个字符「1」「空格」都一样，第三个字符 1 比 2 小，所以「1 120」在前。

要是按「下标序列逐元素比数值」来理解，结论会反过来：[1, 120] 和 [1, 2] 比，第一位相同，第二位 120 大于 2，会选 [1, 2]。两种读法给出的方案不同，而题目要求的是前者。

实测里真的撞到过：一组 16 个工具的数据，最优时间是 15，字符串比较选出「2 4 10 14 16」，逐元素比较选出「2 4 6 10 14 15」。差别就出在下标过了 10 之后，字符串比较是按字符走的，「10」的首字符是 1，比「6」小。

随机小数据（n ≤ 12、下标都是个位数）上两种读法结论不同的比例只有 0.6% 上下，因为个位数下字符串比较和逐元素比较恰好一致。工具数超过 10 之后这个坑才会真正咬人。

七、写错的地方

题目位置写法与正确解不一致的比例
最长递增二分找 <= num 的最右位置53.03%
最长递增还原覆盖式赋值改成只填第一次25.98%
最长递增还原前驱下标漏掉 -174.45%
最长递增dp从左往右填 dp（变成「以 i 结尾」）70.75%
潜水压缩内层 j、k 正着枚举56.93%
潜水转移时间相等时不比方案字符串1.40%（平局极多时 15.50%）
潜水path空方案不特判，直接拼 " " + i85.05%
潜水字典序按下标数值逐元素比较0.58%

「时间相等时不比方案」那条在随机数据上只有 1.40% 的概率被抓到，因为随机生成的 c 很难凑出并列最优。把所有工具的 c 都设成 1 之后再测，抓取率涨到 15.50%。这类错误的特点是：数据不特殊就测不出来，交上去却一定错。

「按下标数值逐元素比较」只有 0.58%，原因上面说过：演示用的都是小数据，下标没超过 9。真实题目里 n 到 100，下标两位数，这个比例会高得多。

八、三维版为什么不划算

不压缩的写法多一维 i，语义直白，代价是空间。n = 100、m = v = 200 时，三维表是 101×201×201 = 4,080,501 格，按 int 算 15.57 MB；压缩之后只剩 201×201 = 40,401 格，0.154 MB，差 100 倍。

时间上三维版 271.62 ms、压缩版 192.92 ms，压缩版还快一点，因为要拷贝的字符串少了。两版的最优值和最优方案实测完全一致。

顺带一提，path 存字符串本身就挺费。真要卡内存可以存「前驱状态 + 本轮选没选」，最后再回溯拼字符串，但那样代码会长一截，这题的数据范围下没必要。

题目版本时间空间

最长递增ends 数组 + 二分O(n log n)O(n)

最长递增那边，n = 10000 时 O(n²) 的写法实测 84.10 ms，二分版 0.20 ms，差 420 倍。n = 1000000 时二分版 23.93 ms。

潜水的时间两版一样，都是 n·m·v 次内层循环；差的只有空间，而空间差正好卡在能不能过题上。

十、总结

方案要「字典序最小」时，思路是先照常把最优值算出来，再让方案的选择跟着这个最优值走。第一题的 dp 值本身带着位置信息，扫一遍就能填出答案；第二题的状态里没有可回溯的维度，只能把方案挂在每个状态上一起更新。

两个容易出错的点：字典序的定义要按题面来，「下标整体当字符串」和「下标序列逐元素比」是两回事；还有覆盖式赋值看着粗暴，其实是靠候选值的单调性保证取到最小，改成「只填一次」就丢了这一层保证。

动态规划大专题里类似的题还有很多，做法都是这个套路的两头：要么状态里留了可回溯的维度，要么额外存一份方案结构。
