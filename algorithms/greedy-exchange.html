贪心：相邻两项比一比

砍树和加工食材看起来是两道毫不相干的题，答案却都藏在同一个动作里：先定下做的顺序，剩下的是一个 01 背包。定顺序的办法也很朴素，只看相邻两项谁先谁后。

零、两道题

砍树：一共 n 棵树，每棵有两个数，第一天的初始重量 init 和每天的增长量 grow。每天最多砍一棵，从第 1 天开始一共有 m 天。第 j 天砍下第 i 棵树的收益是 init[i] + grow[i] × (j - 1)，求 m 天里的最大总收益。

烹调方案：一共 n 个食材，加工必须串行，总时间是 m 秒。第 i 个食材的初始美味是 a[i]，每过一秒衰减 b[i]，加工需要 c[i] 秒。完成时刻为 t 的食材贡献 a[i] - t × b[i]，求最大总美味。

两道题都有一堆东西要挑一部分来做，而且做哪个、第几个做都会影响收益。挑哪些是背包的活，第几个做就是排序的活，得先把顺序定下来。

一、只看相邻两项

假设当前时刻是 s，手上有两个东西 x 和 y，先做哪个？把两种选择的收益都写出来。

先 x 后 y：a[x] - s·b[x] + a[y] - (s + c[x])·b[y] = 公共部分 - c[x]·b[y]

先 y 后 x：a[y] - s·b[y] + a[x] - (s + c[y])·b[x] = 公共部分 - c[y]·b[x]

两式里的公共部分是 a[x] + a[y] - s·b[x] - s·b[y]，它跟谁先谁后没关系，两项各自的初始美味和 s 时刻的衰减都在里面。真正分出高下的只有后面那个乘积项：先做的那个，它的耗时会推后另一个的完成时刻，代价就是自己的耗时乘上对方的衰减速度。

所以判断短得很：c[x] × b[y] ≤ c[y] × b[x] 时先做 x，否则先做 y。这个比较只需要两个东西自己，跟 s、跟别人都无关，于是整张表存在一个全局的先后关系，排一遍就能定下顺序。

这里有个细节值得单独拎出来。比较式两边是两个数相乘，b 到 105 时乘积到 1010，用 32 位整数装会溢出，得用 64 位。

还有一个更容易踩的坑在比较符本身。这个比较式在 C++ 里必须写严格小于，写成 <= 时，两个东西的乘积相等会同时返回「x 在 y 前面」和「y 在 x 前面」，这不是严格弱序，std::sort 遇到这种比较函数行为未定义。实测 n = 50、m = 105 的一组随机数据，写 <= 的版本直接段错误，写 < 的版本正常返回。乘积相等时两个顺序的收益本来相同，取哪个都行，用严格小于把这个歧义交给排序去处理最省事。

二、砍树：初始重量和顺序无关

第 j 天砍第 i 棵树的收益是 init[i] + grow[i] × (j - 1)。初始重量是砍下去就到手的固定数，跟它是第几天砍没关系；拖得越久涨得越多的，是增长量那一项。

所以增长量大的树应该晚砍。把它写成相邻比较：x 和 y 分别在第 j 天和第 j+1 天砍，先 x 后 y 的总收益是 init[x] + grow[x]×(j-1) + init[y] + grow[y]×j，交换过来是 init[y] + grow[y]×(j-1) + init[x] + grow[x]×j，两式相减剩 grow[y] - grow[x]。前一种更好当且仅当 grow[y] < grow[x]，也就是增长量小的排前面。

排完序之后，问题只剩「这 m 天砍哪些树」。天数是一格一格过去的，砍掉一棵树占掉一天，这就是一个 01 背包：

dp[i][j] = max(dp[i-1][j], dp[i-1][j-1] + init[i] + grow[i] × (j-1))

第一项是不砍第 i 棵，第二项是砍，砍它的时候前面已经用掉了 j-1 天，所以它的收益按第 j 天算。按排序后的顺序做这个递推，第 i 棵的「越晚砍」正好对上了。

两个改法都试过。把排序反过来（增长量大的排前面）抓取率 69.59% 到 81.60%；干脆不排序、按输入顺序做背包，抓取率 46.69% 到 61.78%。第二个错法在小数据上也常常蒙对：树少、增长量又碰巧递增时，输入顺序本身就近似排好序了。

// 砍树：每天最多砍 1 棵，第 j 天砍第 i 棵树的收益 = init[i] + grow[i] * (j - 1)
    // 初始重量与顺序无关，增长速度慢的排前面，越靠后的树越该晚砍
    long long maxProfit(vector<int> init, vector<int> grow, int m) {
        int n = init.size();
        vector<int> id(n);
        for (int i = 0; i < n; i++) {
            id[i] = i;
        }
        sort(id.begin(), id.end(), [&](int x, int y) {
            return grow[x] < grow[y];
        });
        // dp[i][j]：用 j 天，从排好序的前 i 棵树里挑着砍，最大收益
        vector<vector<long long>> dp(n + 1, vector<long long>(m + 1, 0));
        for (int i = 1; i <= n; i++) {
            int x = id[i - 1];
            for (int j = 1; j <= m; j++) {
                dp[i][j] = max(dp[i - 1][j], dp[i - 1][j - 1] + init[x] + (long long) grow[x] * (j - 1));
            }
        }
        return dp[n][m];
    }

三、烹调方案：美味按完成时刻算

烹调方案里真正决定收益的是完成时刻。同一个食材，早一秒做完就少衰减一秒。推导上面已经做过，排序键是 c[x]×b[y] < c[y]×b[x]，排好之后同理接一个 01 背包。

这题的背包和砍树有个区别：秒数是连续占用的，而且不要求把 m 秒用满。所以状态记的是「加工总时长恰好为 j」，用 -1 表示这个时长到不了，答案是所有 j 里最大的那个：

dp[j] = max(dp[j], dp[p] + a[i] - j × b[i])，其中 p = j - c[i]，且要求 dp[p] 可达。

一维数组倒着扫就能原地更新，不用开二维表。注意转移里写的是 - j × b[i]，用的就是加完这个食材之后的完成时刻；写成开始时刻 - p × b[i] 是个很自然的笔误，抓取率 85.69%（小值域）到 60.92%（值域 [1, 20]）。

把排序键换成「加工时间短的先做」也能过一部分数据，但抓取率只有 5.74% 到 0.20%，值域越大越抓不到。原因是加工时间短和衰减速度低经常同向，随机数据里两者给出的顺序会碰巧吻合。

// 烹调方案：n 个食材串行加工，一共 m 秒，完成时刻为 t 的食材贡献 a - t * b
    struct Food {
        int a, b, c;
    };
    // x 先做比 y 先做好，当且仅当 c[x] * b[y] < c[y] * b[x]
    // 这个比较符必须是严格弱序，写成 <= 时相等键两个方向都返回 true，std::sort 会崩
    bool cmpFood(const Food &x, const Food &y) {
        return (long long) x.c * y.b < (long long) y.c * x.b;
    }
    long long maxDelicious(vector<Food> food, int m) {
        int n = food.size();
        sort(food.begin(), food.end(), cmpFood);
        // dp[j]：加工总时长恰为 j 时的最大美味，-1 表示这个时长到不了
        vector<long long> dp(m + 1, -1);
        dp[0] = 0;
        for (int i = 0; i < n; i++) {
            for (int j = m, p = j - food[i].c; p >= 0; j--, p--) {
                if (dp[p] != -1) {
                    dp[j] = max(dp[j], dp[p] + food[i].a - (long long) j * food[i].b);
                }
            }
        }
        long long ans = 0;
        for (int j = 1; j <= m; j++) {
            ans = max(ans, dp[j]);
        }
        return ans;
    }

实测砍树在 n = m = 250 时跑完 0.08ms；烹调方案在 n = 50、m = 105 时 1.74ms。单个食材的贡献是 a - t × b，t 和 b 都能到 105，乘出来是 1010，32 位装不下，dp 得用 64 位。

五、对数器怎么抓错

两道题的暴力都不用排序，直接在原数据上穷举出最优答案，贪心才没有机会自我验证。

砍树的暴力是逐天决策：第 d 天选一棵还没砍过的树，或者干脆歇着，dfs 到底取最大值。烹调方案的暴力枚举所有加工序列：每步挑一个没做过的食材接在后面，累计时间超过 m 就停，沿途记录总美味。

排序键的错法抓取率差别很大：砍树那边怎么排都差得远，一改就是七成以上；烹调方案按 c 排序只有 0.20%。这说明抓取率只回答一个问题：这个错法要多特殊的数据才会露出来。它跟错得多离谱是两件事。做对数器的时候值域要铺开，只跑一组随机大数据很可能把错误放过去。

砍树 n = m = 250 时 0.08ms；烹调方案 n = 50、m = 105 时 1.74ms。烹调方案的 dp 数组开了 m + 1 个 64 位整数，m 到 105 时是 800KB 左右。

总结

两道题的顺序都由相邻两项的比较决定。同一时刻的两个东西，先做的那个会推后对方的完成时刻，代价是自己的耗时乘对方的衰减速度，谁先谁后就比这两个乘积。

砍树的比较式化简后是 grow[y] < grow[x]，初始重量与顺序无关，所以增长量小的排前面；烹调方案的排序键是 c[x]×b[y] < c[y]×b[x]，两边都要 64 位，比较符要写严格小于。

顺序定下来之后两题都是 01 背包。砍树按天数递推、收益按第几天算；烹调方案的状态是「总时长恰好为 j」，答案取所有时长里的最大值，美味按完成时刻而不是开始时刻算。
