贪心：两两比较定出的顺序

一组数排个序拼成最大的整数，一群人分成两半飞两座城市。两题看着毫不相干，答案却都是「排一遍、扫一遍」，而且排序的依据都来自同一句话：只盯住两个东西，看它们换个前后会不会更差。

零、答案就是一个顺序

先看第一题。给一组非负整数，把它们重新排列再首尾拼起来，要求拼出的整数最大。

比如 [3, 30, 34, 5, 9]，拼成 9534330。

最直接的做法是把所有排列都枚举一遍，取最大的那个。n 个数有 n! 种排法，n=10 就是 3628800 种，n=20 直接上到 2.4×1018。这条路走不通。

再看一组两个数的例子：[9, 91]。

「谁大谁在前」在这里失效了。原因也不难看出：拼接的时候决定结果的是谁的名字先出现，跟这两个数各自多大没有关系。91 比 9 大，可它一被放在前面，就把 9 挡在了后面。

一、只盯两个数

把「排列」这件事拆开看：任何一串拼接结果，都可以从某个顺序出发，一次次交换相邻两个数得到。而交换相邻的 a、b，只会动到这两个数占的那一段，前后其余部分原样不动。所以只要保证每一对相邻都摆对了，整串就摆对了。

于是问题缩到两个数上：a 和 b，谁在前面更好？比一下就行，a 接 b 得到 a+b，b 接 a 得到 b+a，哪个大，哪种摆法赢。

这里有个细节：这个判据能不能直接交给排序函数？排序函数要求比较关系是传递的，也就是「a 在 b 前、b 在 c 前」推出「a 在 c 前」。光看拼接结果不容易看出传递性，把判据换个写法就清楚了。

记位数 len(a)，则 a+b 这个整数等于 a×10len(b) + b。于是

a+b > b+a ⟺ a×(10len(b)−1) > b×(10len(a)−1) ⟺ a/(10len(a)−1) > b/(10len(b)−1)。

右边是两串实数在比大小，传递性自然成立。也就是说，每个数对应一个权重 w(x) = x/(10len(x)−1)，题目的排序就是把这些权重从大到小排。

9 的权重是 9/9 = 1.000，91 是 91/99 = 0.919；30 是 0.303，3 是 0.333。权重这一栏已经把 9 排在 91 前面、3 排在 30 前面这两件事说清楚了。

顺带说一句，这个权重只是用来解释传递性，代码里不必真算它。浮点数比较有精度风险，直接拼字符串比大小最稳。

二、把判据交给排序

// nums 里都是非负整数，两两拼起来比大小决定谁排前面
    bool cmp(const string& a, const string& b) {
        return a + b > b + a;
    }

    string largestNumber(vector<int>& nums) {
        int n = nums.size();
        vector<string> s(n);
        for (int i = 0; i < n; i++) {
            s[i] = to_string(nums[i]);
        }
        sort(s.begin(), s.end(), cmp);
        if (s[0] == "0") {
            return "0";
        }
        string ans;
        for (int i = 0; i < n; i++) {
            ans += s[i];
        }
        return ans;
    }

两处容易漏的地方。

1）比较用的是字符串拼接结果，不是数值。n 稍大一点结果就长得离谱，实测 n=200000 时拼出来的整数有 180 万位，什么整数类型都装不下。好在 a+b 和 b+a 长度相同，按字典序比字符串和按数值比完全等价，不必转成数字。

2）全 0 要特判。排序之后 s[0] 就是权重最大的那串，如果是 "0"，说明整组全是 0，直接返回 "0"，否则会拼出一串前导零。

实测排序 n=200000 个数（每个最多 9 位）耗时 52.07 ms，n=100000 是 24.70 ms。

三、写错的地方

这道题的错误基本都出在比较依据上。用两万组随机数据量了一下三个常见写法：

按数值降序排，值域 0 到 99 时错 28.54%，值域到 106 时错 32.60%。按字典序降序排，值域到 106 时只错 0.01%，看着像对的，可值域压到 0 到 99 就错到 9.08%。

值域 0 到 9 时三种写法都是 0.00%，因为全是单个数字，怎么排都一样。这提醒了一件事：拿对小数据看着没问题的写法交题，等数据换成两位数就开始错。

漏掉全 0 特判的两万组里只抓出 2.70%：整组数全是 0 的样本占 8.32%，可只有一个数的那种拼出来还是 "0"，真正会拼出多余前导零的是「全 0 且长度大于 1」的样本。这类错误靠随机数据抓不牢，得自己想到。

四、第二题：两地调度

公司要面试 2n 个人，每人两个价格 costs[i] = {飞 A 市的花费, 飞 B 市的花费}，两座城市各去 n 个人，问最小总花费。

朴素做法是枚举哪 n 个人去 B，方案数 C(2n, n)，n=15 时已经是 1.55 亿。

换个视角。先假设所有人都飞 A，总花费是 sum(aCost)。现在把某个人改成飞 B，总花费的变化量是 bCost[i] − aCost[i]，一个固定值，跟别人怎么选没关系。

这一下就清楚了：最终方案与「全飞 A」的差额，正好是「被派去 B 的那 n 个人的差值之和」。要总花费最小，就挑差值最小的 n 个人派去 B。

// costs[i][0] 是第 i 个人飞 A 市的花费，costs[i][1] 是飞 B 市的花费
    // 先假设所有人都飞 A，再看改成飞 B 会让总花费变化多少
    int twoCitySchedCost(vector<vector<int>>& costs) {
        int n = costs.size();
        vector<int> diff(n);
        int sum = 0;
        for (int i = 0; i < n; i++) {
            diff[i] = costs[i][1] - costs[i][0];
            sum += costs[i][0];
        }
        sort(diff.begin(), diff.end());
        for (int i = 0; i < n / 2; i++) {
            sum += diff[i];
        }
        return sum;
    }

样例里全飞 A 要花 470，第 3 个人和第 4 个人差值分别是 −350 和 −10，改成飞 B 之后 470 − 350 − 10 = 110，这就是答案。

排序 2n=200000 个人耗时 12.08 ms，2n=100000 是 6.08 ms。

五、写错的地方

第一个错法最自然也最常出现：让每个人各自挑便宜的那座城。它错在人数约束上，两万组随机数据里错 68.16%（值域 1 到 100）。

第二个错法是差值排反，把差值最大的 n 个人派去 B，错 100.00%。第三个错法按 A 市费用从小到大取前 n 个人飞 A，错 67.54%。这两个错法的共同点是把「挑哪一半」的依据找错了，一个用了反向的键，一个用了另一个字段。

顺便留意值域的影响：每人挑便宜这个错法在值域 1 到 5 时只错 33.71%，值域到 100 以上就稳定在 68% 附近。小值域里两座城市价格经常相等，错法反而容易歪打正着。

六、两个演示

演示 A　把比较判据跑到排序上

相邻两个比一次，拼起来大的那种摆法保留。跑到最后，卡片顺序就是答案。

演示 B　两地调度：从全飞 A 出发

差额按从小到大排好队，前 n 个改飞 B。总费用从「全飞 A」出发，每改一个人就加上他的差额。

七、复杂度分析

题目关键操作时间空间
最大数一次比较器排序 + 一次拼接O(n log n) 次比较，每次比较要拼接两个数O(n)，存下来的字符串
两地调度求差值 + 排序 + 取前 n 个求和O(n log n)O(n)，差值数组

两题都是「排序加一趟扫描」，瓶颈都在排序上。最大数那次排序的比较次数虽然也是 O(n log n)，但每次比较要拼两串字符串，常数比普通整数比较大不少，实测的 52 ms 主要花在这里。

八、总结

1）贪心里有一类题的答案就是一个顺序，做法是排序加扫描。难点不在排序，在排序依据。

2）找依据的办法是只看两个元素：交换相邻两个只影响它们自己那一段，所以任意一对摆对了，整串就摆对了。最大数的依据是 a+b 与 b+a 的大小。

3）判据要能进排序函数，就得是传递的。最大数这一步靠把拼接收缩成一个权重 x/(10len−1) 来看；两地调度靠把「全去 A」当基准，把每个人的贡献拆成一个固定差额。

4）两题各有一个隐蔽角落：最大数要特判全 0，两地调度别让每个人各自挑便宜的城市。前者随机数据抓不到，后者小值域下也抓不牢，都得靠想。

下一类题连依据都不用找：扫的过程中留下一个能随时取出最小值的东西就够了。
