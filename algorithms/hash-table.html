哈希表：桶、扩容与均摊代价

哈希表常被说成 O(1)，严格讲是均摊 O(k)，k 是样本的平均长度。桶开多大、什么时候扩、一次扩多少、桶里挂什么，全是可调的旋钮，但调来调去只影响常数。这一页把桶、拉链、扩容和开放地址都摆出来，让数字自己说话。

零、同一个表，两种哈希函数

100 万个 64 位 key 插进拉链哈希表，再全量查一遍：用 MD5 落桶，插入 198.73 毫秒、查询 11.29 毫秒。把桶的选择改成「所有 key 都进 0 号桶」，插入涨到 33.5 秒，查询 51.9 秒，比较次数是 3166 亿次。

表的结构一模一样，唯一区别是哈希函数把 key 摊开还是堆在一起。所以哈希表的性能问题，一半在哈希函数上。

一、桶数组加链表

哈希表的主体是一个桶数组。key 先用哈希函数变成整数，再对桶数取余得到下标，元素就挂在那个桶里。同一个桶里的多个元素串成一条链，查询时沿链逐个比 key。

// 拉链哈希表：桶里挂链表，装满就翻倍
    size_t cap = 1, sz = 0;
    vector<vector<pair<u64, u64>>> b(1);

    void growTable() {
        vector<vector<pair<u64, u64>>> nb(cap * 2);
        for (size_t i = 0; i < cap; i++)
            for (auto& kv : b[i]) nb[kv.first % (cap * 2)].push_back(kv);
        b.swap(nb); cap *= 2;
    }

    void put(u64 key, u64 val) {
        if ((sz + 1) > 0.75 * cap) growTable();
        auto& chain = b[key % cap];
        for (auto& kv : chain) if (kv.first == key) { kv.second = val; return; }
        chain.push_back({key, val}); sz++;
    }

    bool get(u64 key) {
        for (auto& kv : b[key % cap]) if (kv.first == key) return true;
        return false;
    }

算哈希、取余、沿链比较，这三步构成一次操作。桶数取 2 的幂时 % cap 可以写成 & (cap-1)，编译器也会替你这么改，所以这个取余不是瓶颈。

二、什么时候扩、扩多少

桶太少，链就长，查询退化成遍历链表；桶太多，内存白占。常见做法是给负载因子设一个阈值，元素数超过「桶数 × 阈值」就扩容。

扩容因子是每次把桶数乘几倍。取 2 倍时桶数翻倍，取 1.5 倍时更省内存但要多扩几次。100 万个 key、阈值 0.75，实测三档：

1.515748033523622012.36335.25 ms
1.113536511381015278010.151323.96 ms

扩容因子越小，最终占的内存越少，但扩容次数和搬家总量涨得很快。1.1 倍时扩容 138 次、搬了 1015 万个元素，插入耗时是 2 倍的 5 倍多。这笔账很直白：扩容因子记作 a 时，总搬运量约是元素数的 1/(1−1/a) 倍，a 取 2 是 2 倍量级，取 1.1 就是 10 倍量级。

阈值放到 2.0，桶只用了 52.4 万个、内存省一半，插入反而最快，代价是比较次数从 160 万涨到 343 万、查询慢了一半。阈值 0.5 是反过来的取舍。这几个数字都说明同一件事：阈值在「内存」和「比较次数」之间挪，挪不出复杂度级别。

三、扩容的代价是摊出来的

单看一次扩容，它要新建一个桶数组，把老数组里的每个元素重新算一遍桶位置再挂过去，这一步是 O(元素个数)。如果每次插入都扩，那是灾难。

好在扩容因子大于 1，桶数是指数增长的：1、2、4、8……到第 k 次扩容时桶数是 2k，前 k 次扩容搬走的总元素数不超过最后一次的两倍。100 万个 key 总共搬了 157 万格，平均每次插入只多搬 1.57 格，是个常数。这就是均摊 O(1) 的来源。

真正决定单次操作时间的还是 k。key 越长，算哈希要读的字节越多，链上比较也要按长度比，两者都随 k 增长。拿长度不同的 key 各插 20 万次：

1281.103 微秒

长度涨到 256 倍，时间涨到 9 倍。所以哈希表增删改查的复杂度写 O(k)，k 是样本平均长度；只有当 key 是定长整数这种 k 为常数的场景，才退化成常说的 O(1)。

四、另一种桶：开放地址

不挂链表也能做哈希表。开放地址的思路是「位置被占了就往后找下一个空格」，所有元素都躺在同一个大数组里，省掉了链表的指针开销，缓存也更友好。

// 开放地址：位置被占了就往后找下一个空格
    vector<u64> slot(cap); vector<char> used(cap, 0);

    void put(u64 key) {
        size_t i = key % cap;
        while (used[i]) { if (slot[i] == key) return; i = (i + 1) % cap; }
        used[i] = 1; slot[i] = key;
    }

    bool get(u64 key) {
        size_t i = key % cap;
        while (used[i]) { if (slot[i] == key) return true; i = (i + 1) % cap; }
        return false;   // 遇到第一个空格就说明没有
    }

删除是它的麻烦处：直接把槽清空会切断探测链，后面的元素就找不到了。要么留下墓碑标记，要么定期整理整个表，这一块比拉链版多一份麻烦。

开放地址的性能对装载因子极度敏感。数组长度固定成 100 万，插入不同数量的 key，统计每次操作的平均探测次数：

五、那五个可调的地方

把上面这些串起来，一个哈希表能定制的地方就这五处：初始开多少个桶、链表多长时触发扩容、一次扩多少倍、用哪种哈希函数、桶里挂链表还是开放地址还是红黑树。

工程实现里它们各有各的默认值。比如有的语言在单条链太长时把链转成红黑树，把最坏情况的 O(n) 压到 O(log n)；有的语言把初始桶数设得很小、把阈值调得很大，赌的是「多数哈希表其实很短命」。

但不管怎么定制，能动的只有常数：桶数决定内存，阈值和扩容因子决定搬家总量与链长的取舍，哈希函数决定分布。时间复杂度始终是均摊 O(k)，没有哪一种定制能把它变成别的。

总结

哈希表是桶数组加冲突处理。拉链版每个桶挂一条链，溢出元素串在链上；开放地址把元素都放在同一个数组里，靠向后探测找空位，代价是对装载因子更敏感，装载因子从 0.5 到 0.9 平均探测次数涨了 9 倍。

扩容是哈希表里唯一「昂贵」的动作，但桶数按倍数增长，总搬运量只是元素数的常数倍，摊到每次插入上就是常数。100 万个 key、扩容因子 2 倍时总共搬了 157 万格，平均每插一个多搬 1.57 格。

复杂度写作均摊 O(k)，k 是 key 长度，而不是笼统的 O(1)；key 长度从 8 涨到 2048，单次插入从 0.716 微秒涨到 6.460 微秒。桶数、阈值、扩容因子、哈希函数、桶结构这五处都能调，调的都是常数。哈希函数把 key 摊得多开，决定了这一切能不能成立。
