线段树：势能分析与剪枝

开方和取模这两个操作，都没法用懒标记表示：知道一段的和，推不出每个数开方之后的和。只能下到叶子一个一个算。好在两个操作都在飞快地缩小数值：一个数开方六次就变成 1，取模一次至少减半。拿区间最大值挡一道，整段都不用下。

零、背景

先说清楚难在哪。区间加能懒，是因为「整段加 v」对和的影响是确定的：v 乘段长。开方不行，√(a+b) ≠ √a + √b，知道和不知道每个数各自是多少，就没法算出开方后的和。取模同理。

所以这两题的修改操作，只能一路走到叶子。区间长度 10⁵、操作 10⁵ 次，一次改一个区间就是 10⁵ 个叶子，总共 10¹⁰，做不完。

能救场的是：绝大部分修改其实什么都没改。

一、题目

两个题，形状几乎一样。

  • 开平方：长度 n 的数组，操作 0 把 [l, r] 每个数开平方向下取整，操作 1 查 [l, r] 的累加和。n、m 到 10⁵，arr[i] 到 10¹²。数据里可能出现 l > r，遇到要交换。
  • 取模：长度 n 的数组，操作 1 查 [l, r] 累加和，操作 2 把 [l, r] 每个数对 x 取模，操作 3 把 arr[k] 改成 x。n、m 到 10⁵，和可能超过 int。

二、一个数能开方几次

10¹² 一路开方下去：10¹² → 10⁶ → 1000 → 31 → 5 → 2 → 1，一共六次。到 1 之后 √1 还是 1，再开一百次也是 1。

arr[i] 的上限是 10¹²，所以任何一个位置，真正改变过它的开方操作最多六次。之后那个位置就再也不需要下去了。

这就是势能分析的说法：把一个数离 1 还有多远看成它的势能，每次有效开方把势能砍掉一大截，势能总量一开始最多 n × 6，每次操作真正花钱的地方都是势能下降的地方。

三、拿最大值挡一道

实现上只需要一件事：每个节点除了 sum 再维护一个 max。往下走之前先看一眼，整段最大值 ≤ 1 就不用去了。

// 没有懒更新，也不需要 down
    // 唯一的加速是：整段最大值 <= 1 时，开方等于没开，直接不去
    void doSqrt(int jobl, int jobr, int l, int r, int i) {
        if (l == r) {
            long long v = (long long)sqrt((long double)maxv[i]);
            sum[i] = v;
            maxv[i] = v;
            return;
        }
        int mid = (l + r) >> 1;
        if (jobl <= mid && maxv[i << 1] > 1)
            doSqrt(jobl, jobr, l, mid, i << 1);
        if (jobr > mid && maxv[i << 1 | 1] > 1)
            doSqrt(jobl, jobr, mid + 1, r, i << 1 | 1);
        up(i);
    }

没有懒标记，也就不需要 down。唯一的加速就是那两个 > 1。

挡掉的有多少？n = m = 10⁵，全程只做开方，实测有剪枝时一共只访问了 499980 个叶子，6.9 ms；去掉剪枝，叶子访问 3331864720 个，26919.4 ms。差 3912 倍。

演示：开方时哪些段被剪掉

树里写的是每段的 max。灰色的段是 max ≤ 1、直接跳过的；橙色的段是真的下去改了。连点几次，灰色会越来越多。

四、取模减得更快

取模的缩小速度也能量出来。x ≤ v 时，v % x 一定小于 v 的一半：x ≤ v/2 时余数小于 x 也就小于 v/2；x > v/2 时余数就是 v − x，还是小于 v/2。v 从 1 到 2000、x 从 1 到 v 全部枚举一遍，2 × (v % x) 超过 v 的情况一次都没有。

所以每次「真的把数改小了」的取模，至少把它砍掉一半。int 范围内最多砍 31 次：2147483647 每次对 ⌊v/2⌋ + 1 取模，31 次到 0。

挡的条件也跟着是最大值：x 比整段最大值还大，这一段每个数取模都等于自己，整段跳过。

// x 比整段最大值还大时，每个数取模都等于自己，整段不用动
    void doMod(int jobl, int jobr, long long x, int l, int r, int i) {
        if (x > maxv[i]) return;
        if (l == r) {
            sum[i] %= x;
            maxv[i] = sum[i];
            return;
        }
        int mid = (l + r) >> 1;
        if (jobl <= mid) doMod(jobl, jobr, x, l, mid, i << 1);
        if (jobr > mid)  doMod(jobl, jobr, x, mid + 1, r, i << 1 | 1);
        up(i);
    }

同样的 n = m = 10⁵，全程只做取模，有剪枝访问 459654 个叶子、9.7 ms；无剪枝 3340159801 个、26807.3 ms，差 2772 倍。

五、单点修改会把势能加回来

取模这题还多一个操作 3：把某个位置直接赋成 x。这会把那个位置的势能从「接近 1」拉回 log x。

好在这个操作是单点的。势能一次只涨 log x，沿着一条到根的路径把 max 刷一遍是 O(log n)，所以一次赋值带来的额外代价是 O(log x × log n)。m 次操作最多涨 m 次，总账还是 O((n + m) log V log n) 这个量级。

演示：取模与势能回涨

x 大于整段 max 时整段变灰。预设里有一步单点赋值，赋值之后那一条到根的路径上 max 会重新涨起来，后面的取模就又能下去了。

这里有个细节：赋值之后必须一路 up 把祖先的 max 刷新。max 偏大只会少剪一些枝，答案还是对的；可要是赋值把数改小、max 却停在旧值，那也是白花时间。反过来如果哪个写法让 max 偏小，就会剪掉本该下去的分支，答案直接错。

六、复杂度分析

项开平方取模
单次操作最坏O(n)O(n)
单次查询O(log n)O(log n)
修改的摊还代价O(6 log n) 每位置O(log V log n) 每位置
全程总代价O((n + m) log n log V)O((n + m) log n log V)
空间O(n)：sum 与 max 各一个 long long 数组O(n)：sum 长整型、max 整型

开平方的 log V 实际就是 6，取模的 log V 是 31 上下。n = 10⁵ 时 sum 数组四倍开是 3.2 MB，max 数组再来一份。

两题的实测：n = m = 10⁵，开平方加查询混合 11.78 ms，三种操作混合的取模题 24.77 ms。

七、几种写错的样子

每组 20000 个随机输入。开平方的四档是「n / m / 初值上限」= 4 / 4 / 20、10 / 10 / 1000、30 / 20 / 10⁵、60 / 40 / 10¹²；取模的四档是 4 / 4 / 10、10 / 10 / 100、30 / 20 / 10⁴、60 / 40 / 10⁶。

三行 0.00% 值得单独说一下，它们都是「看着像优化、实际只是变慢」的那一类：

开平方的阈值写成 > 0，max 等于 1 时还是会下去，到叶子算 √1 = 1，等于白跑一趟。答案一点没变，只是把剪枝带来的 3912 倍全丢了。取模不剪枝同理。

取模叶子上不刷新 max 更有意思：max 停在旧的高值，x > max 这个条件更难成立，于是剪枝变弱、多做一些无用功，但因为从没「该下去却没下去」，答案照样对。方向反过来的写法才会出错，就是上面 x ≥ max 那一行。

x ≥ max 为什么错：x 正好等于 max 时，那个最大值取模的结果应该是 0，提前返回就把它留在那了。随机数据下 x 恰好撞上区间最大值不常见，值域一大就更罕见，所以这一行从 6.41% 一路掉到 0.01%。

八、总结

懒标记解决不了的操作，还能靠「这个操作多半什么都没改」来省。做法是给节点多维护一个能判断「整段是否值得下去」的量，这两题都是最大值。

势能分析给的是摊还账：不看单次操作，看全程一共有多少次「真的改到了东西」。开平方每个位置最多六次，取模每次砍一半，所以总量是 O(n log V) 次有效下潜，每次下潜 O(log n)。单点赋值会把某个位置的势能加回来，但一次只加 log V × log n，不影响总账。

剪枝的正确性方向是单向的：判断条件放宽（多下去）只会慢，不会错；判断条件收紧（少下去）就会漏改。写的时候宁可多跑一趟，也别把阈值往上提。

最后

两个实现上的坑。一是这两题都没有 down，别忘了顺手把 down 调用删掉，留着不会报错，只是每多一次函数调用。二是开平方那题的数据里 l 可能大于 r，读进来先交换，否则区间查询会拿着一个左大右小的范围往下走，什么也算不出来。
