动态开点线段树：范围大到开不下也能用

范围是 1 到 10 的 9 次方，四倍长度的静态数组要占 91552.7 MiB，差不多 89 GiB，谁也开不出来。可是操作只有 1000 次，每次真正在树上走的路不超过 60 层。差了五个数量级，就别按范围开空间了：走到哪一段，再给哪一段发一个编号。

零、背景

一棵线段树到底要多少空间，取决于按「范围」算还是按「用过的结点」算。按范围算是 4n 个结点，每个结点要放累加和（8 字节）和懒标记（8 字节），再加左右孩子的编号（各 4 字节），一个结点 24 字节。

把 n 换成具体数字：n 是一百万的时候四倍数组是 91.6 MiB，还能接受；n 是一亿的时候是 9155.3 MiB；n 是十亿的时候是 91552.7 MiB。后面这两个数已经不是「优化一下常数」能解决的了。

另一头是操作数量。一次区间修改在树上走的路，是两条从根到叶子的边线，每层最多两个结点，树高是 log₂n，所以一次操作新碰到的结点不超过 2·log₂n 个。范围十亿的树高只有 30，一千次操作撑死碰到六万个结点，六万个结点每个 24 字节只有 1.7 MB。

两头一比就清楚了：范围大、操作少，按范围开空间是浪费，按操作开空间才对得上。

一、题目

第一题：n 个位置编号 1 到 n，一开始全是 0，一共调用 m 次操作。

  • 操作 1 l r v：把 l 到 r 的每个数加上 v
  • 操作 2 l r：返回 l 到 r 的累加和

其中 1 ≤ n ≤ 10⁹，1 ≤ m ≤ 10³。

第二题：实现一个结构，支持范围是 1 到 10⁹ 的区间，调用加起来 10⁵ 次。

  • add(l, r)：把 l 到 r 范围内的数字都设置成 1
  • count()：返回整个范围内有多少个 1

第二题只有「设置成 1」，没有「设置回 0」，这一点后面会省掉很大一件事。

二、只在不得不去的时候才申请

静态线段树里，i 号结点的两个孩子固定是 i << 1 和 i << 1 | 1。这个规则一去掉，就得自己记孩子的编号。

做法是发号码：变量 cnt 记已经发出去多少个号，1 号给根，之后谁要孩子就 ++cnt 领一个新的。lc[i]、rc[i] 记 i 号结点的左右孩子编号，0 表示这个孩子还从来没有被申请过。

// 范围 1~n，n 可以到 10^9
    // 空间按「操作次数 * 树高 * 2」估，再留一截余量
    const int LIMIT = 80001;

    int cnt;                 // 已经发出的结点编号，1 号是根
    int lc[LIMIT], rc[LIMIT];  // 左右孩子的编号，0 表示还没申请过
    long long sum[LIMIT];      // 这一段的累加和
    long long addTag[LIMIT];   // 这一段挂着的整段加任务

    void clear() {
        fill(lc, lc + LIMIT, 0);
        fill(rc, rc + LIMIT, 0);
        fill(sum, sum + LIMIT, 0);
        fill(addTag, addTag + LIMIT, 0);
        cnt = 1;
    }

建树这一步直接不要了。整棵树只有一个根，根代表的范围是 1 到 n，所有位置的值都是 0。

区间加的写法和静态版差不多，区别只有两句：要往左走之前看一眼 lc[i]，是 0 就领一个号；要往右走之前同样看一眼 rc[i]。

void up(int h, int l, int r) {
        sum[h] = sum[l] + sum[r];
    }

    void lazy(int i, long long v, int n) {
        sum[i] += v * n;
        addTag[i] += v;
    }

    // ln / rn 是左右两段各有多长
    // 下发之前必须先把两孩子申请出来，否则任务没地方放
    void down(int i, int ln, int rn) {
        if (addTag[i] != 0) {
            if (lc[i] == 0) lc[i] = ++cnt;
            if (rc[i] == 0) rc[i] = ++cnt;
            lazy(lc[i], addTag[i], ln);
            lazy(rc[i], addTag[i], rn);
            addTag[i] = 0;
        }
    }
void add(int jobl, int jobr, long long jobv, int l, int r, int i) {
        if (jobl <= l && r <= jobr) {
            lazy(i, jobv, r - l + 1);
        } else {
            int mid = (l + r) >> 1;
            down(i, mid - l + 1, r - mid);
            if (jobl <= mid) {
                if (lc[i] == 0) lc[i] = ++cnt;   // 不得不去左边，才申请左边
                add(jobl, jobr, jobv, l, mid, lc[i]);
            }
            if (jobr > mid) {
                if (rc[i] == 0) rc[i] = ++cnt;   // 不得不去右边，才申请右边
                add(jobl, jobr, jobv, mid + 1, r, rc[i]);
            }
            up(i, lc[i], rc[i]);
        }
    }

查询更省：任务往左拐的时候，如果 lc[i] 还是 0，说明这一整段从头到尾没被碰过，值全是 0，连递归都不用进。

long long query(int jobl, int jobr, int l, int r, int i) {
        if (jobl <= l && r <= jobr) {
            return sum[i];
        }
        int mid = (l + r) >> 1;
        down(i, mid - l + 1, r - mid);
        long long ans = 0;
        // 从来没被申请过的分支，整段都是 0，查都不用查
        if (jobl <= mid && lc[i] != 0) {
            ans += query(jobl, jobr, l, mid, lc[i]);
        }
        if (jobr > mid && rc[i] != 0) {
            ans += query(jobl, jobr, mid + 1, r, rc[i]);
        }
        return ans;
    }

还有一处容易漏。down 要把懒任务交给两个孩子，交之前得先保证孩子存在，所以在 down 里也要申请。任务没地方放，比没申请到编号更麻烦：它会顺着 0 号结点把数据写进一个谁都不读的地方。

三、一次 add 走过的路

拿 n 等于 8 举例，看 add(3, 6, 5) 会把树开成什么样。根是 [1, 8]，中点 4，任务跨过中点，所以左右都要去：[1, 4] 和 [5, 8] 各领一个号。

左边 [1, 4] 只需要它的右半 [3, 4]，于是 [3, 4] 领号，[1, 2] 不存在。右边 [5, 8] 只需要它的左半 [5, 6]，[7, 8] 也不存在。这一趟一共开出 5 个结点，位置 1 和 2 从头到尾没有被访问过。

再来一次 add(7, 8, 2)，这回走着走着要拐进 [7, 8]，它才被申请出来，编号 6。两次操作之后树上是 6 个结点，逐位看是 0、0、5、5、5、5、2、2。

然后查一次 [2, 7]。查到 [7, 8] 这一层时要把它挂着的 2 下发出去，下发前先给两个孩子申请空间，于是 [7, 7] 和 [8, 8] 这两个叶子是查询的时候才出现的。查询本身也会让树长大。

一个细节：up(i, lc[i], rc[i]) 里的 lc[i] 可能是 0，sum[0] 恒为 0，所以不用为「一边不存在」写特判。

演示：按操作顺序看树怎么长出来

范围取 1 到 8，点「下一步」依次执行操作，看每一步新申请了哪些结点、每个位置上是多少。

四、空间要开多大

估法是「操作次数 × 树高 × 2」。实测下来比它略多一点：n 是十亿、m 是一千、操作里三分之二是区间加，三个随机种子分别开出 71841、71956、72028 个结点，平均每个操作开出 71.84 到 72.03 个，单个操作最多开出 103 个。估法给的是 1000 × 30 × 2 = 60000，实际七万二。

所以常量取 80001 只富余一成。操作次数翻倍，这个常量就得跟着翻倍，别写死一个数就不管了。

换小一点的范围，每操作开出的结点数基本跟着树高走：n 是一亿时平均 59.01 个（树高 27），n 是一百万时平均 32.05 个（树高 20）。

时间上：n 是十亿、m 是一千，同一份操作跑 200 遍取最好，开点 0.238 ms。先把所有端点离散化再做普通线段树（离散出 3002 个区间，不含排序去重）是 0.099 ms，只要开点的四成。离散化要先拿到全部操作才能开始，在线读一个做一个的题用不上这条；而且离散化要处理「相邻端点之间那一段」，想清楚它的代价，不如开点来得直接。

五、第二题：连懒更新都不用

第二题的特殊性在于，查询永远只问全量：count() 直接返回 sum[1]。既然不问小区间，就不需要把任务往叶子传，只要根是对的就行。而根是 up 上推出来的，up 一直在保证这件事。

另一个条件是只有「设置成 1」。一段已经全是 1，以后还是 1，往下的任务也就没有意义了。setOne 开头一句「这一段满了就返回」，把整棵树的生长按住了。

// 只有「把一段置 1」，没有「置回 0」
    // 所以整段满了就直接返回，不需要任何懒更新标记
    void up(int h, int l, int r) {
        sum[h] = sum[l] + sum[r];
    }

    void setOne(int jobl, int jobr, int l, int r, int i) {
        if (sum[i] == r - l + 1) {   // 这一段已经全是 1
            return;
        }
        if (jobl <= l && r <= jobr) {
            sum[i] = r - l + 1;
        } else {
            int mid = (l + r) >> 1;
            if (jobl <= mid) {
                if (lc[i] == 0) lc[i] = ++cnt;
                setOne(jobl, jobr, l, mid, lc[i]);
            }
            if (jobr > mid) {
                if (rc[i] == 0) rc[i] = ++cnt;
                setOne(jobl, jobr, mid + 1, r, rc[i]);
            }
            up(i, lc[i], rc[i]);
        }
    }

这句早退有多值钱，看实测。十亿范围、10⁵ 次 add：

  • 区间很长（平均五亿）时，整棵树只开出 459 个结点，早退命中 99986 次，占 99.99%
  • 区间长度不超过一百万时，开出 106643 个结点
  • 区间长度不超过 1000 时，开出 2856171 个结点，早退只命中 0.86%
  • 区间长度不超过 10 时，开出 1759902 个结点
  • 全是单点区间时，开出 1443204 个结点

最后几行藏着一个坑：常见题解里常量写成 700001，随机大区间够用（只要 459 个），区间一短就崩：长度不超过 1000 时要 286 万个结点，全是单点也要 144 万个。拿 700001 的数组跑 10 万次单点 add，进程直接段错误（退出码 139），连一个错误答案的机会都不给你。开点线段树的空间要按操作形状估，不能照抄一个数。

拿有序表（平衡树里存不相交区间，合并之后累加段长）做对照，同样是 10⁵ 次 add 加 10⁵ 次 count：区间很长时有序表 2.660 ms、开点 2.090 ms；区间长度不超过 1000 时有序表 44975.399 ms、开点 28.002 ms；单点区间时有序表 48106.545 ms、开点 18.679 ms。有序表那边的统计是每次把段扫一遍算总数，段数一多就崩。真要在生产里用有序表，得再维护一个总量，那时候大区间场景它会更快。开点线段树贵在常数，赢在分析成本低。

演示：只置 1 的时候，早退把树按住

六、复杂度分析

项第一题（区间加 + 区间求和）第二题（置 1 + 全量计数）
单次操作O(log n)：一路走到底，每层最多两个结点O(log n)，整段已满时 O(1) 返回
建树O(1)，只有一个根
全程总代价O(m log n)
空间O(m log n)：与范围 n 无关，只与操作次数有关

按第一题的数据范围算：m 是 1000、n 是 10⁹，结点上界按 80001 开，四个数组一共 80001 × (4 + 4 + 8 + 8) 字节，约 1.83 MiB。第二题按 10⁵ 次操作估，最费空间的是长度一千左右的区间，要 286 万个结点，三个 int 数组约 32.7 MiB。

空间不再出现 n，这是开点线段树唯一真正的好处。时间复杂度和静态版完全一样，常数还大一点（每次访问多一次间接寻址），所以范围开得下的题别用它。

七、几种写错的样子

第一种：查询时不判断 lc[i] 是不是 0，照常递归进去。400 组随机测试里答案一次没错，结点数也一个没多，正确版和错法版都是平均 63.60 个。能兜住是因为 0 号结点自始至终没人写过，没申请过的分支读出来恒是 0，正好是求和题的单位元；可这是拿哨兵赌正确性，哪天有别的代码往 0 号结点写进一个数，所有查询跟着一起错。白付的代价是时间：每次查询都要往这些没申请过的分支里白跑一趟，深度和树高一样。

第二种：down 里直接把任务交给 lc[i]，忘了先申请。400 组里 364 组出错，一共 4542 处错误答案，编号数掉到 58.22。任务全写进了 0 号结点，它的两个孩子被反复申请，树等于没建。

第三种：号码领好了，递归的时候却照堆式编号写 i << 1。400 组里 368 组出错。开点线段树的编号和位置没关系，任何一处按 2i 推算都是错的。

第四种是第二题专属：忘了调 up。3 万次 add 里 30000 次对不上，第一次 add 就现形（根是 0，应为 1）。

第五种也是第二题：把「整段已满就返回」那句删了。看着像只是少了个优化，其实它会把答案算错。删掉之后，一个已经被整段置 1 的结点在遇到新的部分覆盖任务时，会去申请只走了一边的孩子，再用 up 把两边加起来，另一边还是 0，老数据就这么丢了。实测：区间长度不超过 1000 时 3 万次 add 有 29980 次对不上，第一次现形在第 21 次；开出的结点从 4128 涨到 113676，耗时从 0.949 ms 涨到 6.221 ms（各跑 5 遍取最好）。区间全是单点时这句早退从来不触发，删不删结果一模一样，都是 91208 个结点、0 次对不上，这也是它在小样例上容易蒙混过关的原因。

八、总结

开点线段树把「按范围开空间」换成「按操作开空间」。结点编号靠 cnt 自增发放，lc、rc 记孩子，0 表示没申请过。改动集中在三处：递归前申请孩子、down 里申请孩子、查询时遇到 0 直接跳过。

第二题示范了另一件事：操作的形状决定结构能省到什么程度。只有置 1、只问全量，就能连懒更新一起不要，还顺手用一个早退把树的大小按在几百个结点上。

代价要记清楚：常数比静态版差，空间估错了会直接越界。能离散化、能用有序表的题，开点往往不是最优解，只是想起来最省事的解。

最后

一是空间常量要按「操作次数 × 树高 × 2」自己估，再留两成以上的余量，别照抄 80001 或 700001。

二是 down 里那两个申请不能省，省了会让任务写进 0 号结点。

三是第二题的早退不是优化，它和「只置 1、只问全量」这两条性质绑在一起，删掉会算错。
