前 k 小子序列和：背包做不了，换堆

给一个非负数组，返回所有子序列（含空集）的累加和里最小的 k 个。n = 105、nums[i] = 106、k = 105。用 01 背包算出每个和出现几次，表长是全部数的总和加一，这个规模下要 186.8 GB，根本开不出来。换个思路之后是 3.548 毫秒加 3.758 毫秒。

零、先确认背包为什么不行

01 背包能回答「累加和恰好是 j 的子序列有多少个」，于是从小到大扫一遍 j，每个 j 出现几次就输出几次，凑够 k 个停手。思路没问题，问题在表长。

// 01 背包版：先算出每个累加和出现了几次，再从小到大数 k 个
    // 表长是「全部数的累加和 + 1」，n 与数值一大就开不出来
    vector<int> topKSumByBag(vector<int>& nums, int k) {
        int sum = 0;
        for (int num : nums) sum += num;
        vector<int> dp(sum + 1, 0);
        dp[0] = 1;
        for (int num : nums) {
            for (int j = sum; j >= num; j--) dp[j] += dp[j - num];
        }
        vector<int> ans;
        for (int j = 0; j <= sum && (int)ans.size() < k; j++) {
            for (int c = 0; c < dp[j] && (int)ans.size() < k; c++) ans.push_back(j);
        }
        return ans;
    }

表长是 sum + 1，sum 是所有元素的总和。n = 105、每个元素 106 时 sum 是 5.0 × 1010，光这一维数组就是 186.8 GB。n = 104 也还要 18.6 GB。

就算把规模压到能跑：n = 2000、sum = 101031 的小数据下，01 背包要 61.080 毫秒，堆只要 0.073 毫秒，差了 837 倍。时间上也没得比。

背包的问题在于它把「所有可能的和」都排了一遍，可我们只需要最小的 k 个。和的取值范围远大于 k，绝大部分格子是白算的。

一、堆：每次只推出两个后继

先把数组排序。堆里放的是一个二元组 (right, sum)，含义是「有一个子序列，它用到的最右下标是 right，累加和是 sum」，按 sum 从小到大弹。

从只含 nums[0] 的那个子序列出发（右端 0、和 nums[0]）。每次弹出堆顶，就得到下一个最小的和，然后把它推出两个后继：

1）把最右那个元素换成下一个：(right + 1, sum - nums[right] + nums[right + 1])，子序列长度不变；

2）在最右边追加一个：(right + 1, sum + nums[right + 1])，子序列长度加一。

两个操作都保持「最右下标」这个性质成立，也都不会回头去动已经确定的左边部分。可以证明每个非空子序列都恰好被生成一次：任何一个子序列都能从「只含它的最右元素」开始，反复用操作 1 把右端一步步挪过去。

空集的和是 0，它是第 1 小，不用进堆，直接写在答案第 0 位。于是循环跑 k − 1 次就得到全部 k 个。

// 堆版：排序之后，堆里放 (子序列最右下标, 累加和)
    // 弹出一个，就把它「换掉最右那个」和「再追加一个」两个后继推回堆里
    // ans[0] = 0 是空集，所以第 1 小不用从堆里取
    struct PairCmp {                                  // 只按累加和排序，别顺手用 greater<pair>
        bool operator()(const pair<int, long long>& a, const pair<int, long long>& b) const {
            return a.second > b.second;               // greater<pair> 会先比下标，那不是我们要的顺序
        }
    };

    vector<long long> topKSum(vector<int> nums, int k) {
        sort(nums.begin(), nums.end());               // 必须先排序，否则推出的顺序不是从小到大
        priority_queue<pair<int, long long>, vector<pair<int, long long>>, PairCmp> heap;
        heap.push({0, nums[0]});                      // 只含 nums[0] 这一个子序列
        vector<long long> ans(k, 0);
        for (int i = 1; i < k; i++) {
            auto cur = heap.top();
            heap.pop();
            int right = cur.first;
            long long sum = cur.second;
            ans[i] = sum;
            if (right + 1 < (int)nums.size()) {
                heap.push({right + 1, sum - nums[right] + nums[right + 1]});  // 换掉最右那个
                heap.push({right + 1, sum + nums[right + 1]});                // 再追加一个
            }
        }
        return ans;
    }

实测 n = 105、k = 105：排序 3.548 毫秒，堆那 k 次弹出 3.758 毫秒，堆里最多同时存 105 个元素。n = 104 时是 0.280 毫秒加 4.663 毫秒。

演示一：堆里每次弹一个、推两个

二、排序那一步不能省

上面那两个后继操作，只有在数组有序的时候才能保证「弹出的顺序就是从小到大的顺序」。操作 1 把 nums[right] 换成 nums[right + 1]，换上来的数必须不小于换下去的，新和才不小于旧和。数组没排过序，这条就不成立，堆顶也就不是下一个最小的了。

实测两万组随机样本（n 在 2 到 8），不排序直接跑有 86.97% 的样本答案和真值不同。这个比例高得离谱，随手一组数据就能撞上。

反例小到三个数。nums = [5, 1, 3]，真值的前 8 小是 0 1 3 4 5 6 8 9；不排序跑出来是 0 5 1 3 4 6 8 9，第二个位置就是 5，可 1 比它小得多。排序之后 [1, 3, 5] 才对得上。

三、第 K 大和：取绝对值再减回来

换一道题：数组里的数可正可负，求第 k 大的子序列和。

先把所有正数加起来，记成 sum，这是第 1 大（全选正数，不选负数和 0）。第 2 大要么是从 sum 里去掉一个最小的正数，要么是 sum 加上某些非正数。两种说法可以合成一句：第 k 大 = sum − 某个用「绝对值」凑出来的最小代价。

把所有数取绝对值得到数组 a，那么：

nums 的第 k 大子序列和 = sum − a 的第 k 小子序列和

其中 a 的第 1 小是空集的 0，对应 nums 的第 1 大 sum。这条关系成立的原因是，选一个负数等于从 sum 里减掉它的绝对值，不选一个正数也等于减掉它自己。

于是问题回到上一节的堆，只是堆的初始元素从「只含 a[0] 的子序列」换成空集 (-1, 0)，下标 −1 表示空。多出来的一个细节：扩展操作 1（换掉最右那个）在 idx = −1 时没有意义，要跳过，否则会去读 a[−1]。

struct Node {
        long long val;    // 用绝对值数组凑出来的累加和
        int idx;          // 当前子序列用到的最右下标，空集是 -1
    };
    struct NodeCmp {
        bool operator()(const Node& a, const Node& b) const {
            if (a.val != b.val) return a.val > b.val;
            return a.idx > b.idx;
        }
    };

    // 第 k 大子序列和 = 所有正数之和 - 绝对值数组的第 k 小子序列和
    long long kSum(vector<int> nums, int k) {
        int n = nums.size();
        long long sum = 0;
        for (int i = 0; i < n; i++) {
            if (nums[i] > 0) sum += nums[i];
            else nums[i] = -nums[i];                  // 负数取绝对值，正数照抄
        }
        sort(nums.begin(), nums.end());
        priority_queue<Node, vector<Node>, NodeCmp> heap;
        heap.push({0, -1});                           // 空集，累加和 0，第 1 小
        for (int i = 1; i < k; i++) {                 // 弹掉前 k-1 小
            Node cur = heap.top();
            heap.pop();
            if (cur.idx + 1 < n) {
                heap.push({cur.val + nums[cur.idx + 1], cur.idx + 1});          // 追加
                if (cur.idx >= 0) {                                             // 换掉最右那个
                    heap.push({cur.val - nums[cur.idx] + nums[cur.idx + 1], cur.idx + 1});
                }
            }
        }
        return sum - heap.top().val;                  // 堆顶就是第 k 小
    }

这个判断漏掉的后果很直接：实测两万组随机样本，63.86% 出错。LC2386 的样例 nums = [2, 4, −2]、k = 5，正确答案是 2，没有这个保护会算出 4。

实测 n = 105、k = 105：排序 6.100 毫秒，堆那一段 10.840 毫秒，堆大小稳定在 105 左右。

四、复杂度分析

做法时间额外空间说明
枚举全部子序列O(2n)O(2n)先全算出来再排序，n = 20 就一百万个
01 背包O(n · sum)O(sum)表长是总和加一，n = 105 时要 186.8 GB
排序 + 堆O(n log n + k log k)O(k)每次弹出推两个，堆里最多 2k 个元素

堆那一栏的 k log k 来自 k 次堆操作，每次 O(log k)；堆里元素个数的上界是 2k，因为每弹一个最多推两个回来。n log n 是排序。

k 可以超过 2n 吗？题目里 k ≤ 105，而 n = 105 时子序列个数是 2100000，远远够取。反过来 n 很小的时候（比如 n = 10）子序列只有 1024 个，k 取 105 就没有意义，题目会保证 k 不超过这个数。

五、总结

这两道题的共同点是「要的只有前 k 个，而可能的取值远多于 k 个」。背包的思路是把所有取值都算一遍，堆的思路是每次只推出紧挨着的下一个。

几个要记住的点：

1）堆里存二元组（最右下标, 累加和），弹出时推两个后继：换掉最右那个、再追加一个。空集的和 0 是第 1 小，不进堆。

2）数组必须先排序。少了这一步，两万组随机样本里 86.97% 出错，反例 [5,1,3] 第二个位置就错。

3）第 K 大和那题把「第 k 大」换成「sum 减去绝对值数组的第 k 小」，堆的初始元素换成空集 (−1, 0)。

4）idx = −1 时不能做「换掉最右那个」的扩展。漏掉这个判断，两万组里 63.86% 出错。

5）用 greater<pair> 当堆的比较器会先比下标，这里要的是只按累加和排序，得自己写比较器。

这类「第 k 小 / 第 k 大」的问题还有不少变体，核心都是找一个能把候选按顺序推出来的后继关系。
