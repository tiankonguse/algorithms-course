位图

存 1 亿个「有 / 没有」的标记，char 数组要 96 MB，位图只要 12 MB。给 1 千万个数判重，哈希集合跑 979 毫秒，位图 23 毫秒。这一讲看位图怎么用一个 uint32 装 32 个标记，四个操作各长什么样，以及三个容易写错的地方：向上取整会溢出、最后一个 uint32 里有多出来的位、翻转全体为什么能做到 O(1)。

零、背景

先看一个具体问题：给 1 千万个取值在 0 到 10⁸−1 之间的数，问每个数是不是第一次出现。四种做法的实测结果：

做法耗时相对位图存了什么
位图23.12 ms1 倍10⁸ 个位，12 MB
char 数组57.75 ms2.5 倍10⁸ 个字节，96 MB
先排序再去重501.47 ms21.7 倍1 千万个 int，40 MB
哈希集合979.17 ms42.4 倍1 千万个节点，512 MB

快慢的差别出在存法上。位图是一串 bit，第 i 个 bit 记「i 在不在集合里」，一个数占一个位。char 数组一个数占一个字节，哈希集合一个数占一个节点，节点里还得存指向下一个节点的指针，桶数组另算。位图没这些开销，一个数就是一位，没有前后指针，没有哈希函数。

代价是值域必须连续、范围必须事先知道。位图只支持 0 到 n−1，n = 10⁸ 开 12 MB，n = 10⁹ 开 119 MB，再往上就得换思路了。

一、问题与三种存法

要支持的就四件事：把 num 加进去、删掉、有就删没有就加、问 num 在不在。四个操作都得是 O(1)。

空间这块值得单独量一下。同样是「1 亿个有或没有」，实测的常驻内存：

哈希集合那一栏只存了 1 千万个「存在」的数就已经 512 MB，是位图存 1 亿个位的 42 倍。这也是为什么位图常出现在「值域大、个数多、只问有没有」的场景里。

二、位图的形态

用一个 unsigned 数组装。一个 unsigned 是 32 位，能装 32 个标记，第 k 个 unsigned 管 32k 到 32k + 31 这 32 个数。

num 落在哪：第 num / 32 个 unsigned 的第 num % 32 位。32 是 2 的 5 次方，所以除 32 写成 num >> 5，对 32 取余写成 num & 31（留下低 5 位）。num 非负时这两条跟除法取余完全等价。

数组类型写成 unsigned 而不是 int，理由在第 31 位上。1 << 31 在有符号 int 里得到 −2147483648，位模式倒是对的（0x80000000），所以四个操作照用位运算也能算出正确结果（三个种子各 2 万次随机操作，0 处不一致）。麻烦在于那个格子从此是个负数：打印出来是 −2147483648，拿去做任何算术、比较或者判空都会出问题。写成 1u << 31 得到 2147483648，干净。

三、四个操作

四个操作各一行，改的都是同一个 uint32 上的同一位：

#include <bits/stdc++.h>
    using namespace std;

    // 位图：只支持 0 ~ n-1
    class Bitset {
    public:
        vector<unsigned> set;

        // n 个位需要 (n + 31) / 32 个 uint32
        Bitset(int n) { set.assign((n + 31) / 32, 0); }

        void add(int num) { set[num >> 5] |= 1u << (num & 31); }

        void remove(int num) { set[num >> 5] &= ~(1u << (num & 31)); }

        void reverse(int num) { set[num >> 5] ^= 1u << (num & 31); }

        bool contains(int num) { return (set[num >> 5] & (1u << (num & 31))) != 0; }
    };

remove 里的 ~ 不能省。~00010000 是 11101111，只有目标位是 0，与上去刚好清掉目标位而不碰别的位。写成 &= 00010000 会把其它位一起清掉。

reverse 用异或，那一位是 1 就变 0、是 0 就变 1，正好对上「有就删没有就加」。它和 remove 只差一个运算符，写的时候别顺手。

四、向上取整与多出来的位

n 个位需要 ⌈n / 32⌉ 个 unsigned。常见的写法是 (n + 31) / 32，n 小的时候没问题，n 接近 int 上限就炸了：

n + 31 在 n ≥ 2147483617 时溢出成负数，拿这个负数去开数组，vector 直接抛异常。改成 n == 0 ? 0 : (n - 1) / 32 + 1 就全程安全：n = 32 得 1，n = 33 得 2，n = 2147483647 得 67108864（256 MB）。顺带一句，n / 32 + 1 也对，但 n 是 32 的倍数时会多开一个 unsigned。

第二个坑在最后一个 unsigned 上。n = 70 要 3 个 unsigned，一共 96 位，比 70 多出 26 位。这 26 位平时是 0，contains 也永远问不到它们（下标最大是 69），所以相安无事。但 flip 之后就露馅了：把每个 unsigned 全部翻成 1，popcount 从头数到尾是 96，真实的 1 只有 70 个，多出 26。

所以按 popcount 数 1 的时候，最后一个 unsigned 要单独把多余位掩掉：

// 两个位图求交：一次算 32 位，比逐位问 contains 快两个数量级
    int intersect(const vector<unsigned>& a, const vector<unsigned>& b) {
        int cnt = 0;
        for (size_t k = 0; k < a.size(); k++) {
            cnt += __builtin_popcount(a[k] & b[k]);
        }
        return cnt;
    }

    // 数 1 的个数时要跳过最后一个 uint32 里多出来的位
    int countAll(const vector<unsigned>& set, int n) {
        int words = n >> 5, rest = n & 31;
        int cnt = 0;
        for (int k = 0; k < words; k++) cnt += __builtin_popcount(set[k]);
        if (rest > 0) cnt += __builtin_popcount(set[words] & ((1u << rest) - 1));
        return cnt;
    }

五、批量操作：一次算 32 位

位图还有一个容易被忽略的好处：集合运算可以一次算 32 个。两个位图求交，逐位问 contains 要 n 次，把两个 unsigned 与起来再 popcount 只要 n / 32 次。

实测 n = 10⁷、两个位图各放 300 万个数：逐位 18.03 毫秒，32 位一组 0.0211 毫秒，855 倍。省掉的是「一个一个问」这件事本身，一次 & 顶 32 次判断，一次 popcount 顶 32 次取位。

同样的思路也能用在全扫上。n = 10⁸ 的位图里数 1 的个数，扫 312.5 万个 unsigned 用 0.17 毫秒；char 数组要扫 10⁸ 个字节，2.51 毫秒，差 14.8 倍。这个差距来自内存带宽：位图要读的字节数只有 char 数组的八分之一。

六、设计位图：flip 的懒标记

再看一道具体的题：设计一个类，支持把某位设 1、设 0、翻转全体、问是不是全 1、问有没有 1、数 1 的个数、输出所有位的状态。前两个和刚才的 add / remove 一样，麻烦在「翻转全体」。

真翻一遍要动 n 个位，也就是 n / 32 个 unsigned。n = 10⁷ 时一轮要扫 312501 个 unsigned，跑 1000 轮 flip 实测 18.357 毫秒。

换个记法就不必翻了。加一个标记 rev，它记的是「底层存的这些位，含义是不是反过来了」：

rev 为 false 时，位上的 1 表示存在；rev 为 true 时，位上的 0 表示存在。flip 于是不用碰任何一位，只做两件事：rev 取反，zeros 与 ones 交换。n = 10⁷ 跑 1000 轮实测 0.005 毫秒。

代价转嫁到了 fix 和 unfix 上：它们要先看 rev，才知道「设成存在」该写 1 还是写 0。

    // 把 i 这位设成「存在」。rev == false 时存在是 1，rev == true 时存在是 0
        void fix(int i) {
            int idx = i >> 5, bit = i & 31;
            if (!rev) {
                if ((set[idx] & (1u << bit)) == 0) {
                    zeros--;
                    ones++;
                    set[idx] |= 1u << bit;
                }
            } else {
                if ((set[idx] & (1u << bit)) != 0) {
                    zeros--;
                    ones++;
                    set[idx] ^= 1u << bit;
                }
            }
        }

        void unfix(int i) {
            int idx = i >> 5, bit = i & 31;
            if (!rev) {
                if ((set[idx] & (1u << bit)) != 0) {
                    ones--;
                    zeros++;
                    set[idx] ^= 1u << bit;
                }
            } else {
                if ((set[idx] & (1u << bit)) == 0) {
                    ones--;
                    zeros++;
                    set[idx] |= 1u << bit;
                }
            }
        }

两个分支里那层 if 也不能省。zeros 和 ones 是跟着位走的，重复 fix 同一个位置时位没变，计数就不该动；多减一次 zeros，后面 all() 和 count() 全跟着错。

剩下几个操作都只读 ones 和 rev，不碰底层数组：

    // 翻全局：只翻标记，再交换 zeros 与 ones
        void flip() {
            rev = !rev;
            swap(zeros, ones);
        }

        bool all() { return ones == size; }

        bool one() { return ones > 0; }

        int count() { return ones; }

        // 输出时按 rev 决定要不要把每一位再翻回来
        string toString() {
            string s;
            s.reserve(size);
            for (int i = 0, k = 0; i < size; k++) {
                unsigned number = set[k];
                for (int j = 0; j < 32 && i < size; j++, i++) {
                    s.push_back(char('0' + (((number >> j) & 1) ^ (rev ? 1 : 0))));
                }
            }
            return s;
        }

toString 是唯一一个必须回到 O(n) 的地方：每一位都要输出，输出多少位就得走多少步，这个省不掉。它按 rev 决定要不要把取出来的位再翻一次。

七、复杂度分析

设值域是 0 到 n−1，哈希集合里已有 k 个元素：

操作位图哈希集合说明
add / remove / reverse / containsO(1)期望 O(1)位图是两次运算：num >> 5 定 unsigned，掩码定位
初始化O(n / 32)O(1)要把每个 unsigned 清 0，n = 10⁹ 时要清 3125 万个
空间O(n / 8) 字节O(k) 个节点1 亿个位 12 MB；哈希集合 1 千万个 int 要 512 MB
flip（懒标记）O(1)无此操作真翻每一位是 O(n / 32)，n = 10⁷ 时慢 3600 倍
求交 / 求并O(n / 32)O(k)一次 AND 顶 32 次查询，n = 10⁷ 时快 855 倍
countO(n / 32)，popcount 全程O(k) 或 O(1) 记账位图靠 popcount 扫，也可像设计位图那样记账
toStringO(n)O(n)输出多少位就得走多少步，省不掉

空间那一行是位图真正的卖点：O(n / 8) 字节，跟集合里实际有多少个元素无关。哈希集合是 O(k)，元素越多越占地方。反过来说，值域大但元素稀疏时位图就亏了：n = 10⁹ 只存 100 个数，也要开 119 MB。

时间上要说实话：单点随机访问，位图和 char 数组基本打平（n = 10⁶ 混合 1 千万次操作：位图 41.44 毫秒，char 数组 40.06 毫秒）。位图拉开差距要靠批量操作和大值域：n = 10⁸ 的随机访问位图 5.05 毫秒、char 数组 23.73 毫秒；全扫一遍数 1 是 0.17 毫秒对 2.51 毫秒。

八、总结

要点列一下：

1）位图是一串 bit，第 i 位记 i 在不在集合里。定位用 num >> 5（第几个 unsigned）和 num & 31（第几位）。

2）四个操作分别是 |= 1u << bit、&= ~(1u << bit)、^= 1u << bit、& (1u << bit)。数组写 unsigned，1 << 31 会得到一个负数。

3）开数组的长度用 (n - 1) / 32 + 1，(n + 31) / 32 在 n 接近 int 上限时溢出成负数。

4）最后一个 unsigned 里有多出来的位，按 popcount 数 1 时要单独掩掉。

5）集合运算一次算 32 位，一次 & 加一次 popcount 顶 32 次 contains。

6）翻转全体不必真翻，加一个 rev 标记加 zeros / ones 两个计数器就行，flip 变 O(1)。

再往后，位图还有两个方向。一个是布尔过滤：允许少量误判、不许漏判，就能用多个哈希函数把任意值压进一个位图，空间再降一个数量级。另一个是把它当集合用在动态规划里，状态压缩那一类题会反复见到。这两块留到后面讲。
