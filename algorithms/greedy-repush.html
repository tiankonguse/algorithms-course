贪心：堆顶弹出来改一改

一道题要在 k 个列表之间来回取数，一道题要把 n 个人一个个分到项目里。两道题的堆都在做同一件事：把当前最该动的那一个弹出来，改掉它的状态，再放回去重新排队。

零、两道题各自要什么

先看第一题。有 k 个非递减排列的整数列表，从每个列表里挑一个数，让挑出来的 k 个数里最大值减最小值最小，返回这个区间。宽度相同时取左端点更小的那个。

拿 [[4,10,15,24,26], [0,9,12,20], [5,18,22,30]] 走一遍。答案是 [20,24]，宽度 4，三个列表里分别有 20、24、22 落在里面。

第二题换成一个花的钱的问题。景区有 m 个项目，第 i 个项目有两个参数：折扣系数 Ki 和票价 Bi。x 个人一起买这个项目的票，单张票价是 Bi − Ki·x，总花费是 max{x·(Bi − Ki·x), 0}。票价降到负数就按 0 算，等于让项目倒贴钱这种事不承认。

单位有 n 个人，每人最多挑一个项目，也可以不挑。所有人的选择明晚才交上来，你要先准备好钱，所以要求的是「所有分配方式里总花费的最大值」，也就是最坏情况。

两道题隔得很远，但都有同一个动作：手里握着一批候选，每一轮只动其中最好的那一个。

一、最小区间：堆里每个列表放一个候选

「每个列表至少有一个数落在区间里」这句话，反过来就是：区间要盖住每一个列表。

每个列表的指针先停在最左边的数，k 个候选全丢进小根堆。之后每一轮做三件事：堆顶就是当前最小的候选，把它和「堆里当前最大值」凑成一段候选区间，比已经记下的更窄就更新答案；然后把这个候选所属列表的指针往后挪一格，把下一个数补进堆；任何一个列表被走完就停。

为什么每一轮只看「最小值到最大值」这一段就够了？

设这一轮堆里的最小值是 L。任何一个盖住所有列表的区间，只要它包含 L，就必须包含每个列表里第一个不小于 L 的数，否则那个列表就没有元素落进来。这些数里最大的那个是堆里的最大值 M，所以右端点至少是 M。而 [L, M] 本身确实盖住了所有列表，它就是左端点取 L 时最窄的那个区间。

剩下的问题是：这些 L 有没有被漏掉。堆顶每次都是「还没被当作左端点考虑过的数里最小的那个」，因为一个数被弹出之后，它的位置只会由它后面更大的数接手。所以每一轮都在枚举下一个可能的左端点，一个不漏。

// 最小区间：k 个非递减列表各取一个数，让这些数的最大值减最小值最小
    struct Node {
        int v;  // 值
        int i;  // 来自哪个列表
        int j;  // 来自该列表的哪个位置
    };
    vector<int> smallestRange(vector<vector<int>>& nums) {
        int k = nums.size();
        // 小根堆按值比；值相同的按列表编号比，不然相等的元素会互相顶掉
        auto cmp = [](const Node& a, const Node& b) {
            return a.v != b.v ? a.v > b.v : a.i > b.i;
        };
        priority_queue<Node, vector<Node>, decltype(cmp)> heap(cmp);
        int mx = INT_MIN;
        for (int i = 0; i < k; i++) {
            heap.push({nums[i][0], i, 0});
            mx = max(mx, nums[i][0]);
        }
        int best = INT_MAX, lo = 0, hi = 0;
        while ((int)heap.size() == k) {  // 堆里少一个列表就说明有列表走完了
            Node minNode = heap.top();
            heap.pop();
            if (mx - minNode.v < best) {  // 堆顶是最小值，mx 是当前最大值
                best = mx - minNode.v;
                lo = minNode.v;
                hi = mx;
            }
            if (minNode.j + 1 < (int)nums[minNode.i].size()) {
                int nv = nums[minNode.i][minNode.j + 1];
                heap.push({nv, minNode.i, minNode.j + 1});
                mx = max(mx, nv);
            }
        }
        return {lo, hi};
    }

二、组团买票：一个人值多少钱

第二题的关键是算清楚「再来一个人，这个项目多收多少钱」。

项目已经打算去 p 个人，总花费是 p·(B − K·p)。再来一个人，票价掉到 B − K·(p+1)：新来的这位按新价付一份，之前那 p 个人每人少付 K。所以多收的钱是 B − K(p+1) − K·p = B − K(2p+1)。这个数只跟 p 有关，跟别的项目无关。

每送一个人，这个项目的 p 就加一，下一次的增量比这一次少 2K。所以每个项目的增量序列都是递减的：前一个增量一定不小于后一个。把它当成「每个项目提供一串数，必须从前往后取」，那全局最大值就是每次取当前所有可取的数里最大的那个。

大根堆正好在做这件事。堆顶是当下增量最大的项目，弹出来把这一份钱加进答案，人数加一（它的增量变小了），再放回堆里继续和别人比。堆顶的增量一旦不大于 0，说明剩下的机会全是倒贴，收手。

为什么「每次挑增量最大的」就是最大值？把 n 个人分给各项目，等价于在每个项目的递减序列上从前往后各取若干个。既然每个序列都是递减的，靠前的增量永远不小于靠后的，那么「取全局最大的那些增量」这件事本身就不会破坏「先取前一个才能取后一个」的规则。一个一个挑、每次挑当前最大的，取出来的就是全局最大的那 n 个正增量。

// 组团买票：n 个人每人最多挑一个项目，返回最坏情况下要准备多少钱
    struct Game {
        long long ki;   // 折扣系数
        long long bi;   // 门票原价
        int people;     // 已经打算去的人数
        // 再来一个人，这个项目多收多少钱
        long long earn() const {
            return bi - (long long)(people + 1) * ki - (long long)people * ki;
        }
    };
    long long enough(long long n, vector<pair<long long, long long>>& games) {
        auto cmp = [](const Game& a, const Game& b) { return a.earn() < b.earn(); };
        priority_queue<Game, vector<Game>, decltype(cmp)> heap(cmp);  // 大根堆
        for (auto& g : games) {
            heap.push({g.first, g.second, 0});
        }
        long long ans = 0;
        for (long long i = 0; i < n; i++) {
            if (heap.top().earn() <= 0) {  // 再来人只会倒贴，收手
                break;
            }
            Game cur = heap.top();
            heap.pop();
            ans += cur.earn();
            cur.people++;
            heap.push(cur);  // 人数加一之后边际变小，放回堆里重新比
        }
        return ans;
    }

题面说 N、Ki、Bi 都能到 105，答案是 64 位量级。先算一下上界：单个项目取 K = 1、B = 105，第 5 万个人的增量正好为 0，一路加到 5 万人，总花费 5×104 × 5×104 = 2.5×109。这个数已经超过 2147483647。实测把它塞进 32 位整数会得到 −1794967296，符号都翻了。所以这里用 64 位。

四、对数器怎么抓错

最小区间 2 万组随机数据，k 不超过 5、每个列表不超过 3 个数：

错法值域 3值域 1000
弹出最小的之后忘了把该列表的下一个补进堆45.22%61.71%
少了「堆里还有 k 个」这道闸，列表走完还继续弹90.03%99.97%

第二种错法更彻底：某个列表走完之后堆里的窗口已经盖不住所有列表了，算出来的宽度偏小，答案就偏小。值域越大偏得越厉害，因为值域大的时候两个候选很容易拉开差距。

组团买票 2 万组随机数据，m 不超过 3、n 不超过 6：

错法值域 4值域 1000
把 n 个人一次全塞给当前增量最大的项目46.05%48.30%
堆顶增量掉了负数也不收手74.84%70.76%

第一种错法的抓取率几乎不随值域变化，一直卡在一半左右：项目只有 2 到 3 个时，一次全塞正好也是最优解的概率不算低。第二种错法稳定在七成上下，因为增量转负之后加进去的是负贡献，等于自己给自己扣钱。

复杂度分析

题目关键操作时间空间
最小区间n 个数字各进堆一次、出堆一次O(n log k)O(k)，堆里只有 k 个候选
组团买票建堆 m 次，每个人一次弹出加放回O(m log m + n log m)O(m)

最小区间的堆操作次数是死的：每个数字只被压进堆一次，也只会被弹出一次。n = 105、k = 103 实测 1.07ms；把 k 拉到和 n 一样大（每个列表只有一个数）是 1.34ms，因为 log k 只从 10 涨到 17。

组团买票 n = m = 105 实测 12.18ms，答案 6176596433，又是一个 32 位装不下的数。把 K 换成负数（在线测试里就是这么设的）是 8.50ms，因为增量转负之后所有项目都很快失去资格，循环提前结束。

总结

两道题的堆结构不一样，用法是一套。最小区间里堆存的是「每个列表的当前指针」，弹出最小值之后就推进那个指针；组团买票里堆存的是「每个项目的当前增量」，弹出最大值之后就把人数加一、增量变小再放回去。共同点是每弹一次都要改状态、都要放回。

设计这类贪心可以按三步走：先想清楚「候选是什么」和「堆顶代表什么」；再想清楚「弹出去之后状态怎么变」；最后用对数器确认「每次挑最优」不会错过更好的组合。最小区间这一步靠的是「固定左端点后右端点被唯一确定」，组团买票靠的是「增量递减」，两次论证都落在同一个模式上：局部最优能持续成立，是因为候选的代价是单调的。
